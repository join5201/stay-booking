# 이력서 프로젝트 블록. 숙박 예약 서비스 stay-booking

최종 갱신: 2026-09-16 (초안 1. 기간 2026.08.26부터 확정. 포트폴리오 제목 셋이 이 블록의 2, 4, 6번 줄이다)

이력서의 Projects 맨 위에 넣는다. 가장 좋은 카드가 첫 화면에 와야 하므로 MSA 전환 프로젝트보다 앞이다. 줄 일곱 중 1번이 기본기, 2번부터 6번이 문제 해결, 7번이 규모 가정이다.

숙박 예약 서비스 stay-booking
호스트가 숙소와 객실 타입과 날짜별 재고와 요금을 열고 게스트가 예약하고 결제하는 O2O 숙박 예약 서비스입니다. 이벤트 스토밍부터 애그리거트와 계약 설계를 거쳐 백엔드 전부를 구현했습니다.
개발 기간: 2026.08.26 ~ 진행 중
역할: 설계, 백엔드, 프론트, AI 개발 워크플로우 (1인)
기술 스택: Java 21, Spring Boot 4.1.1, Spring Data JPA, MySQL 9.7 (Docker), JUnit 5, Next.js 16, TypeScript, TanStack Query 5, Vitest, MSW, Node (검사 스크립트)
링크: https://github.com/join5201/stay-booking

1. 바운디드 컨텍스트 6개와 커맨드 22개를 이벤트 스토밍과 CRC와 계약(DbC) 문서로 확정하고, 컨텍스트별 domain, application, api, infrastructure 네 층에 검증 책임(형식은 컨트롤러, 규칙은 애그리거트, 컨텍스트를 넘는 선행조건은 앱 서비스, 유일성은 DB)을 배치해 REST API 33개와 내부 처리 4개를 구현, 검증 시나리오 30개 통과와 테스트 454건
2. 같은 날짜 객실에 예약이 몰리면 초과 판매나 교착이 나는 문제를 날짜별 재고 행의 비관적 잠금과 전역 잠금 순서(예약, 결제, 재고 날짜 오름차순)로 막고 실제 MySQL의 두 트랜잭션 경합 테스트 4건으로 고정 [채울 것: k6 동시 N명 선점에서 초과 판매 0, 교착 0, p95]
3. 결제 승인과 예약 만료가 같은 순간 겹치면 순서에 따라 확정과 환불로 갈리던 문제를 기준 시점을 승인 기록의 서버 시각 하나로 통일해 어느 순서든 결과 하나로 만듦
4. 재시도로 같은 예약 요청이 두 번 오면 예약이 둘 생기는 문제를 멱등키 기록의 선행 커밋과 본문 해시 대조와 유니크 충돌 승자 판정으로 막아 예약 요청과 결제 요청과 취소가 같은 실행기를 지나게 함. 같은 키 재전송은 최초 응답을 Idempotency-Replayed 헤더와 함께 재전송
5. 호스트 둘이 같은 숙소를 동시에 고치면 뒤의 저장이 앞을 덮던 문제를 JPA @Version 낙관적 잠금과 409 응답으로 막고, 프론트는 새로 읽어 내가 안 건드린 필드만 새 기준으로 합치게 함
6. AI 코드 생성의 범위 이탈과 자기 채점 문제를 계획 승인 게이트, 생성과 독립 리뷰어 둘과 사람 결정의 역할 분리, 형식과 결정 대조 검사기로 막아 블라인드 리뷰 5회 지적 47건 중 치명 7건을 배포 전 발견하고 반영으로 테스트 35건 추가
7. [채울 것: 예상 규모 가정. 예를 들어 객실 타입 N개, 피크 예약 요청 N TPS, vCPU N과 메모리 N GB 기준 k6 결과]

기존 이력서의 문제, 원인, 해결, 결과 네 줄 형식으로 펴려면 2번, 4번, 6번 각각을 그 네 줄로 늘린다. 재료는 포트폴리오 초안 1절, 2절, 3절의 상세 표다.

Skills 표에 더할 것: Backend 줄에 Java 21, Spring Boot 4, Infra 줄에 MySQL 잠금과 격리 수준, Tools 줄에 k6 [채울 것: 실제로 돌린 뒤에만]. Frontend 줄은 백엔드 지원이므로 맨 아래 한 줄로 Next.js 16, TypeScript, TanStack Query 5.
