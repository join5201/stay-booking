## 2. 섹션 배경색

스티키 색상과 섹션 배경색은 의미가 다르다. 게다가 영역마다 배경색이 뜻하는 바가 다르므로 섞어 읽지 않는다.

### 영역 3의 배경색은 액터의 종류를 뜻한다 (2026-09-01 v3: 유형 4종으로 확장)

자료 04의 액터 정의(시스템 경계 밖의 요청자)를 그대로 적용한 결과다. 여기서 밖이란 컨텍스트 경계의 밖이다. 그래서 다른 컨텍스트도 액터가 된다.

| 배경 | 액터 유형 | 레인 | 비고 |
|---|---|---|---|
| 노랑 계열 | 사람 | 호스트, 운영자, 게스트 | |
| 분홍 계열 | 외부 시스템 | 외부 결제 | |
| 연파랑 | 다른 컨텍스트 | 예약 컨텍스트 | v3 추가. 재고에 HoldInventory, CommitInventory, ReleaseInventory를, 결제에 RefundPayment를 보낸다 (v5) |
| 흰색 | 정책 (스케줄러 포함) | 시스템, 스케줄러 | 아무도 밖에서 요청하지 않았는데 커맨드가 나가는 곳. 스케줄러는 시간을 트리거로 쓰는 정책이다 (v5) |

흰색 두 레인의 빈자리는 Step 8에서 보라색 정책 스티키가 채운다. 지금 비어 있는 것이 정상이며, 액터를 억지로 채워 넣으면 개념이 틀어진다.

영역 3은 손대지 않는다 (v5 확정). v3에서 예약 컨텍스트 레인을 영역 3에 덧붙이려 했으나, 이후 Hold 흡수로 영역 3의 이름 자체가 옛 것이 되어 부분 갱신의 의미가 없어졌다. 영역 3은 Step 3 시점 기록으로 두고, 다른 컨텍스트 액터는 영역 4의 각 섹션 의존 줄에 나타난다. 위 표의 예약 컨텍스트 레인은 영역 4 이후의 개념이다.

### 영역 1~3과 영역 4 이후의 이름이 다른 이유 (2026-09-01 v4 추가)

재검증에서 Hold를 Booking에 흡수하기로 결정했다. 그 결과 이벤트가 24개에서 22개, 커맨드가 23개에서 22개가 됐다.

| 영역 1~3 (Step 3까지의 기록) | 영역 4 이후 |
|---|---|
| StayHeld + BookingCreated | BookingCreated |
| HoldExpired, HoldReleased | BookingExpired |
| ExpireHold, ReleaseHold | ExpireBooking(reason) |
| ReleaseInventory (시스템 레인) | ReleaseInventory (예약 컨텍스트가 재고에 보냄) |
| RequestPayment (게스트 레인) | 그대로 게스트. 예약 컨텍스트가 총액을 붙여 결제로 중계 |
| Hold 섹션 (영역 2) | 없음. Booking에 포함 |

영역 1~3은 그 시점의 판단 기록이므로 고치지 않는다. 왜 바뀌었는지는 03-o2o-event-storming.md 핫스팟 3과 02-o2o-feature-list.md 3-5에 있다.

### 영역 2의 배경색은 컨텍스트 후보를 뜻한다

| 배경 | 엔티티 | 컨텍스트 후보 |
|---|---|---|
| 연주황 | Property, RoomType | 숙소 카탈로그 |
| 연노랑 | DailyInventory, DailyRate | 재고와 요금 |
| 연보라 | Promotion | 프로모션 |
| 연파랑 | Hold, Booking | 예약 (v4: Hold는 Booking에 흡수됨. 영역 2는 기록으로 유지) |
| 연초록 | Payment | 결제 |

Step 4 결과 이 묶음 5개가 그대로 바운디드 컨텍스트가 됐다. 검색은 엔티티가 없으므로 영역 2에는 없고 영역 4에 읽기 모델로만 나타난다.

### 영역 4의 배경색은 바운디드 컨텍스트를 뜻한다 (2026-09-01 v3 추가)

영역 2와 같은 색을 쓴다. 영역 2의 후보가 영역 4에서 확정됐다는 뜻이다.

| 배경 | 컨텍스트 | 성격 |
|---|---|---|
| 연주황 | 숙소 카탈로그 (Catalog) | 컨텍스트 |
| 연노랑 | 재고와 요금 (Inventory) | 컨텍스트 |
| 연보라 | 프로모션 (Promotion) | 컨텍스트 |
| 연파랑 | 예약 (Booking) | 컨텍스트 |
| 연초록 | 결제 (Payment) | 컨텍스트 |
| 회색 | 검색 (Search) | 읽기 모델. 컨텍스트가 아니라서 섹션 배경은 회색이고, 안의 조회 항목 스티키는 초록이다 |

## 3. 보드 영역 구조 (2026-09-01 v3: 숫자와 영역 4 갱신)

단계가 진행될 때마다 오른쪽으로 이어 붙인다. 이전 영역은 수정하지 않고 그대로 둔다. 단, 이후 단계에서 요소가 늘어나면 해당 영역에 레인이나 스티키를 덧붙이는 것은 허용한다. 기존 스티키를 옮기거나 지우는 것은 하지 않는다.

| 영역 | 이름 | 내용 | x 좌표 |
|---|---|---|---|
| 1 | 액터별 타임라인 | 도메인 이벤트 24개 + 핫스팟 6개 (Step 3 시점 이름) | 100 |
| 2 | 엔티티별 그룹 | 이벤트를 애그리거트 후보 8개로 묶은 예비 뷰 (Step 3 시점) | 2800 |
| 3 | 책임-협력 지도 | 커맨드 23개 + 이벤트 24개, 액터 7레인 2행 (Step 3 시점) | 4300 |
| 4 | 바운디드 컨텍스트 | 컨텍스트 5개 + 읽기 모델 1개. 커맨드 22개, 이벤트 22개. 각 섹션에 소유 데이터, 커맨드, 이벤트, 의존 | 5800 |
| 5 | 컨텍스트 맵 | 영역 4 위에 화살표와 관계 유형(Step 5) | 영역 4에 덧붙임 |
| 6 | 애그리거트와 CRC | 애그리거트 경계, CRC 카드 | 예정 |
| 7 | 정책 지도 | Policy와 Saga | 예정 |

### 영역 4 섹션 내부 구성 (2026-09-01 v3 추가)

컨텍스트 섹션 하나는 4줄이다.

| 줄 | 스티키 색 | 내용 |
|---|---|---|
| 소유 데이터 | 회색 | 이 컨텍스트만 쓸 수 있는 데이터. 다른 컨텍스트는 읽기만 |
| 커맨드 | 파랑 | 이 컨텍스트가 받는 커맨드 |
| 이벤트 | 주황 | 이 컨텍스트가 내는 이벤트 |
| 의존 | 회색 | 보내는 커맨드(→)와 구독하는 이벤트(←) |

섹션 바깥 하단에 빨강 핫스팟으로 경계 판정 근거를 둔다. 왜 선점이 재고의 수량이 아니라 예약의 상태인지, 왜 검색이 컨텍스트가 아닌지 등.

### 영역 1과 영역 3의 배치가 다른 이유

같은 이벤트가 두 영역에서 다른 레인에 있다. 불일치가 아니라 관점이 다르기 때문이다.

| 이벤트 | 영역 1 | 영역 3 | 이유 |
|---|---|---|---|
| BookingConfirmed | 게스트 | 시스템 | 영역 1은 게스트 여정의 시간순, 영역 3은 커맨드를 보낸 주체 기준 |
| PaymentRefunded | 외부 결제 | 시스템 | 같음. 환불을 실행하는 커맨드는 정책이 보낸다 |

영역 1은 Step 1 시점의 기록이고 이후 단계의 결정을 소급해 반영하지 않는다. 진행 과정 자체가 남아야 나중에 왜 그렇게 결정했는지 추적할 수 있다.

## 4. 표기 규칙

### 스티키 텍스트 형식

```
EventName
한국어 의미
```

### 특수 표기

| 표기 | 의미 |
|---|---|
| `★ PIVOTAL` | 전후로 도메인의 성격이 뒤집히는 이벤트 (BookingConfirmed) |
| 커맨드가 두 이벤트에 걸침 | 커맨드 하나가 이벤트 둘을 발생시킴 (영역 3의 RequestBooking. 영역 4 이후에는 없음) |
| `× N` | 숙박 날짜 수만큼 반복되는 커맨드 또는 이벤트 (HoldInventory × N) |

### 동사 표기 (2026-09-07)

[이벤트 스토밍](C:/Dev/potenup/99_projects/o2o/03-o2o-event-storming.md)의 동사 규칙을 따른다.

| 영어 | 한국어 | 쓰는 곳 |
|---|---|---|
| Register / Create / Open | 등록 / 생성 / 개설 | 카탈로그 / 프로모션 / 재고 |
| Update | 수정 | 서술적 속성 |
| Adjust | 조정 | 수량, 금액 |
| Hold | 선점 | 재고, 예약 |
| Commit | 확정 (재고) | heldCount → soldCount |
| Confirm | 확정 (예약) | 계약 성립 |
| Release | 반환 | 재고 (예약 쪽 해제는 Hold 흡수로 사라짐) |
| Expire, Close, Cancel | 만료, 종료, 취소 | 예약(HELD) / 프로모션 / 예약(CONFIRMED) |

변경이라는 표기는 쓰지 않는다.

## 5. 보드와 API 명세의 관계 (2026-09-07)

보드는 설계 단계의 커맨드와 이벤트를 표시한다. API에는 조회와 로컬 Mock 경로도 있으므로 API 33개와 커맨드 및 이벤트 22개를 같은 수로 맞추지 않는다.

Hold, Confirm, 재고 반환과 환불은 내부 처리다. 각각을 외부 HTTP 경로로 추가하지 않는다. 영역 1~3의 과거 Hold 이름을 현재 구현 자원으로 다시 만들지 않는다.

이 문서의 영역 번호는 로컬 범례 기준이다. 이번 수정에서 원격 FigJam 보드를 열거나 변경하지 않았다. 영역 6과 7의 예정 표시는 애그리거트 및 정책 산출물의 존재나 완료를 보장하지 않는다.
