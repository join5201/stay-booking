# O2O 서비스 형태 정리

작성일: 2026-08-25

문서 구분: 서비스 유형을 비교하는 학습 참고 자료다. 아래 주문 상태, 기술 예시와 시장 동향을 이번 숙박 서비스의 구현 요구사항으로 사용하지 않는다.

이번 프로젝트는 날짜별 객실 재고를 선점하는 숙박 예약형이다. 예약 상태는 HELD, CONFIRMED, CANCELED, EXPIRED이고 결제와 환불은 Mock이다. 배차, 배달, 채팅, 정산과 광고 기능은 이번 API 범위에 없다.

## 1. 한 줄 정리

O2O는 온라인에서 발생한 수요를 오프라인의 실물 자원(매장, 재고, 사람, 차량, 공간)에 연결해 거래를 완결시키는 플랫폼이며, 그 형태는 결국 누가 이동하는가 + 자원을 어떻게 점유하는가 두 가지로 갈린다.

## 2. 기초: 왜 형태가 갈리는가

일반 이커머스는 재고와 배송만 관리하면 되지만, O2O는 아래 세 가지가 추가된다.

- 자원의 유한성: 좌석, 객실, 기사, 라이더, 시술 슬롯은 복제가 불가능하다. 동시성 제어가 필수다.
- 실시간 상태: 매장 영업 여부, 조리 상태, 기사 위치는 초 단위로 변한다. 상태 동기화가 필요하다.
- 3자 구조: 수요자 / 공급자(사장님, 기사) / 플랫폼이 각각 앱을 갖는다. 하나의 주문이 3개 클라이언트에 서로 다른 뷰로 노출된다.

이 세 제약을 어떻게 푸느냐에 따라 서비스 형태가 나뉜다.

## 3. O2O를 가르는 4개의 축

### 축 1. 오프라인 접점의 위치 (누가 이동하는가)

| 형태 | 이동 주체 | 대표 서비스 | 핵심 과제 |
|---|---|---|---|
| 방문형 | 고객이 매장으로 | 네이버 지도 예약, 캐치테이블, 야놀자, 여기어때, 똑닥 | 미래 시점 자원 예약, 노쇼 관리 |
| 배송형 | 상품이 고객에게 | 배달의민족, 쿠팡이츠, 요기요, B마트 | 주문 상태 머신, 배차, 조리 ETA |
| 방문 서비스형 | 공급자가 고객에게 | 청소연구소, 미소, 숨고, 카카오T 대리 | 인력 스케줄링, 지역 커버리지 |
| 접점 이동형 | 양쪽이 한 지점에서 만남 | 카카오T 택시, 쏘카, 당근 직거래 | 실시간 위치, 매칭 알고리즘 |

### 축 2. 매칭 방식 (백엔드 설계에 가장 큰 영향)

| 방식 | 시간축 | 대표 | 백엔드 코어 |
|---|---|---|---|
| 예약형 | 미래 시점 선점 | 숙박, 병원, 레스토랑, 렌터카 | 재고/슬롯 동시성, 락, 취소 정책 |
| 즉시 주문형 | 지금 접수 후 수 분~수십 분 | 음식 배달, 퀵커머스 | 주문 상태 머신, 이벤트 발행, SLA |
| 실시간 배차형 | 초 단위 매칭 | 택시, 대리, 라이더 배차 | 위치 스트리밍, 지오 인덱스, 매칭 큐 |
| 게시/탐색형 | 비동기, 시간 제약 없음 | 당근, 직방, 숨고 | 검색 랭킹, 채팅, 광고 노출 |

같은 음식 도메인이라도 매장 예약은 예약형, 배달은 즉시 주문형이다. 도메인이 아니라 이 축으로 묶어야 설계가 재사용된다.

### 축 3. 공급 통제 수준

| 유형 | 설명 | 예시 | 트레이드오프 |
|---|---|---|---|
| 순수 중개형 | 매칭만 하고 이행은 공급자가 | 초기 요기요, 숨고 | 진입 쉬움, 품질 편차 큼 |
| 이행 통제형 | 배송망/기사를 플랫폼이 직접 운영 | 쿠팡이츠, 배민 알뜰배달 | 품질 통제, 고정비 부담 |
| 직매입형 | 재고까지 플랫폼이 보유 | B마트, 컬리 | 마진 확보, 물류센터 자본 필요 |

O2O 경쟁의 승부는 광고가 아니라 공급 경쟁력에서 갈린다는 것이 지난 10년간 반복 확인된 패턴이다. 중개형으로 시작해 이행 통제형으로 내려가는 흐름이 일반적이다.

### 축 4. 수익 모델

- 중개 수수료: 거래액 기반 (배달, 숙박)
- 광고: 노출/입점 광고. 당근처럼 거래 수수료 없이 광고만으로 수익화하는 형태도 있다
- 구독: 배민클럽, 쿠팡 와우 등 배달비 락인
- 이용료/배달비: 건당 과금
- 직매입 마진: B마트형
- 리드 판매: 숨고처럼 견적 요청을 전문가에게 판매

## 4. 도메인별 카테고리 지도

과기정통부 O2O 서비스 산업 조사의 분류 기준을 따르면 아래 6~8개로 정리된다.

| 분야 | 대표 서비스 | 접점 | 매칭 | 주 수익 |
|---|---|---|---|---|
| 식품/음식 | 배달의민족, 쿠팡이츠, 요기요, 땡겨요 | 배송형 | 즉시 주문 | 수수료 + 광고 + 구독 |
| 모빌리티/물류 | 카카오T, 쏘카, 티맵, 퀵서비스 | 접점 이동형 | 실시간 배차 | 호출료 + 수수료 |
| 숙박/레저 | 야놀자, 여기어때, 에어비앤비 | 방문형 | 예약 | 수수료 + 광고 |
| 부동산 | 직방, 다방, 호갱노노 | 방문형 | 게시/탐색 | 광고(중개사 대상) |
| 생활 서비스 | 청소연구소, 미소, 세탁특공대 | 방문 서비스형 | 예약 | 수수료 |
| 인력 중개 | 숨고, 크몽, 알바몬 | 방문 서비스형 | 게시/탐색 | 리드 판매 + 수수료 |
| 뷰티/헬스케어 | 똑닥, 강남언니, 굿닥 | 방문형 | 예약 | 광고 + 수수료 |
| 하이퍼로컬 | 당근 | 접점 이동형 | 게시/탐색 | 광고 |

거래액 기준으로는 부동산과 모빌리티가 크고, 매출액(플랫폼이 실제로 가져가는 몫) 기준으로는 식품/음식이 가장 크다. 거래액과 매출액을 구분해서 봐야 한다.

## 5. 백엔드 관점: 유형별로 달라지는 것

| 유형 | 핵심 데이터 모델 | 동시성 이슈 | 인프라 특징 |
|---|---|---|---|
| 예약형 | 슬롯/재고 테이블 (자원 x 시간) | 같은 슬롯 중복 예약. 유니크 제약 + 비관적 락 | 트래픽 예측 가능, 오픈런 시 스파이크 |
| 즉시 주문형 | 주문 + 상태 이력 | 중복 결제/중복 접수. 멱등키 필수 | 피크 시간대(점심/저녁) 집중 |
| 실시간 배차형 | 위치 스트림 + 매칭 큐 | 한 기사에게 중복 배차 | WebSocket, Redis GEO, 쓰기 부하 큼 |
| 게시/탐색형 | 게시글 + 검색 인덱스 | 상대적으로 낮음 | Elasticsearch, 랭킹/추천 비중 큼 |

공통 코어는 주문(또는 예약) 상태 머신이다. 유형에 따라 상태 집합만 바뀔 뿐 구조는 같다.

```java
// 주문 상태 전이 규칙을 enum에 가둬서 잘못된 전이를 컴파일 이후 단계에서 차단
public enum OrderStatus {
    CREATED, PAID, ACCEPTED, COOKING, PICKED_UP, DELIVERED, CANCELED;

    private static final Map<OrderStatus, Set<OrderStatus>> ALLOWED = Map.of(
        CREATED,   EnumSet.of(PAID, CANCELED),
        PAID,      EnumSet.of(ACCEPTED, CANCELED),
        ACCEPTED,  EnumSet.of(COOKING, CANCELED),
        COOKING,   EnumSet.of(PICKED_UP),
        PICKED_UP, EnumSet.of(DELIVERED),
        DELIVERED, EnumSet.noneOf(OrderStatus.class),
        CANCELED,  EnumSet.noneOf(OrderStatus.class)
    );

    public boolean canMoveTo(OrderStatus next) {
        return ALLOWED.getOrDefault(this, Set.of()).contains(next);
    }
}
```

```java
@Service
@RequiredArgsConstructor
public class OrderStatusService {

    private final OrderRepository orderRepository;
    private final ApplicationEventPublisher eventPublisher;

    @Transactional
    public void changeStatus(Long orderId, OrderStatus next, String requestKey) {
        // 비관적 락: 사장님 앱과 라이더 앱이 동시에 상태를 바꾸는 경합 차단
        Order order = orderRepository.findByIdForUpdate(orderId)
            .orElseThrow(() -> new OrderNotFoundException(orderId));

        // 멱등성: 네트워크 재시도로 같은 요청이 두 번 와도 한 번만 반영
        if (order.isAlreadyApplied(requestKey)) {
            return;
        }
        if (!order.getStatus().canMoveTo(next)) {
            throw new InvalidStatusTransitionException(order.getStatus(), next);
        }

        order.changeStatus(next, requestKey);
        // 알림, 정산, 통계는 이벤트로 분리해 주문 트랜잭션을 짧게 유지
        eventPublisher.publishEvent(new OrderStatusChangedEvent(orderId, next));
    }
}
```

예약형은 위 상태 집합이 REQUESTED / CONFIRMED / NO_SHOW / COMPLETED 로 바뀌고, 락 대상이 주문이 아니라 슬롯이 된다. 배차형은 상태 머신 앞단에 매칭 큐가 붙는다.

## 6. 2025~2026 흐름

- 무료배달이 기본값이 되면서 배달비 자체는 더 이상 차별화 수단이 아니게 되었고, 경쟁축이 구독 멤버십 락인으로 이동했다. 배민 58~60%, 쿠팡이츠 25~27%, 요기요 12~14% 수준의 3강 구도.
- 배달앱이 생활 반경 플랫폼으로 확장 중이다. 음식만으로는 주 2~3회에 그치니 장보기, 생필품, 반려동물용품, 전통시장, 편의점까지 붙여 접속 빈도를 올리는 전략.
- 퀵커머스(B마트, 배민스토어, 쿠팡 퀵배송)가 배송형 O2O의 주전장이 되었다. 다크스토어 재고 관리가 새로운 백엔드 과제.
- 진입점이 앱에서 검색/지도로 옮겨가는 중이다. 네이버 지도에 쿠폰을 붙여 탐색 단계에서 혜택을 노출하는 방식.
- 공공 O2O(땡겨요, 배달특급, 서울배달+, 지역화폐 연계)가 수수료 대안으로 자리 잡았다.
- 당근처럼 거래 수수료 없이 지역 광고 플랫폼으로 수익화하는 모델이 별도 축으로 성립했다.

## 7. 이어서 볼 키워드

- Saga 패턴 / 분산 트랜잭션: 주문 - 결제 - 정산이 서로 다른 서비스일 때
- Redis GEO와 지오해시: 실시간 배차와 근처 매장 검색
- Outbox 패턴: 주문 상태 변경과 이벤트 발행의 원자성 보장
