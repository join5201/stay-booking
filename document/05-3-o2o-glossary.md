# O2O 컨텍스트별 용어 사전 (Step 4-3)

최초 작성: 2026-09-01 (05-o2o-glossary.md 1, 3~8절로 작성)

## 1. 액터 (2026-09-02 v8: 게스트를 이용자로)

| 한국어 | 영문 | 정의 |
|---|---|---|
| 이용자 | User | 숙소를 예약하고 결제하는 사람. 호스트와 운영자도 넓게는 사용자지만 이 프로젝트에서 이용자는 예약하는 쪽만 가리킨다. v1에서는 userId로만 식별하고 회원 정보는 다루지 않는다 |
| 호스트 | Host | 숙소를 등록하고 재고와 요금을 관리하는 사람 |
| 운영자 | Operator | 플랫폼 측에서 프로모션을 만드는 사람 |
| 외부 PG | Payment Gateway | 결제를 실제로 처리하는 외부 시스템. 우리에게 결과를 통보한다 |

개명 이력: 게스트(Guest)에서 v8에 변경. 03, 04 등 상류 문서와 보드의 게스트 표기는 그 시점 기록으로 남아 있다.

## 2. 숙소 카탈로그 용어

| 한국어 | 영문 | 정의 |
|---|---|---|
| 숙소 | Property | 판매 대상이 되는 건물 또는 시설 단위. 하나의 주소와 지역을 가진다 |
| 객실 타입 | RoomType | 숙소가 판매하는 객실의 종류 |
| 호실 | Room | 실제 배정되는 개별 방. v1 범위 밖이라 쓰지 않는다 |
| 최대 인원 | maxOccupancy | 객실 타입 하나에 묵을 수 있는 최대 인원. 예약의 인원 검증에 쓰인다. 0보다 크다. 하향 수정은 허용되며 기존 확정 예약에 영향을 주지 않는다 |
| 등록 | Register | 판매 대상을 카탈로그에 새로 올리는 것. 새 식별자가 발급되며 같은 대상을 두 번 등록할 수 없다. 수량이나 금액을 만드는 개설, 등록과는 대상이 다르다 |
| 수정 | Update | 이미 등록된 대상의 서술적 속성을 고치는 것. 식별자는 바뀌지 않는다. 수량과 금액을 고치는 조정과 구분된다 |

## 3. 재고와 요금 용어

| 한국어 | 영문 | 정의 |
|---|---|---|
| 재고 | Inventory | 특정 객실 타입의 특정 날짜에 저장된 판매 가능 수량 |
| 가용성 | Availability | totalCount에서 soldCount와 heldCount를 뺀 계산 결과. 저장하지 않는다 |
| 총 수량 | totalCount | 그날 팔 수 있는 전체 객실 수 |
| 판매 수 | soldCount | 확정된 예약이 점유한 수 |
| 선점 수 | heldCount | 선점이 임시로 점유한 수 |
| 개설 | Open | 기간을 지정해 날짜별 재고를 한꺼번에 만드는 것 |
| 조정 | Adjust | 수량이나 금액을 고치는 것. 불변식 검사가 따른다 |
| 선점 | Hold | heldCount를 올리는 것 |
| 확정 | Commit | heldCount를 내리고 soldCount를 올리는 것 |
| 반환 | Release | heldCount 또는 soldCount를 내리는 것 |
| 반환 원천 | source | ReleaseInventory가 내릴 카운터를 지정하는 값. HELD 또는 SOLD |
| 요금 | Rate | 호스트가 등록한 날짜별 1박 단가. 0보다 크다 |

재고와 가용성을 구분하는 것이 이 컨텍스트의 핵심이다. 재고는 저장된 값이고 가용성은 매번 계산되는 값이다.

## 4. 프로모션 용어

| 한국어 | 영문 | 정의 |
|---|---|---|
| 프로모션 | Promotion | 운영자가 만든 자동 적용 할인 정책 |
| 적용 조건 | Condition | 최소 숙박일, 지역, 기간 |
| 할인율 | discountRate | 정률 할인의 비율 |
| 캠페인 기간 | campaignPeriod | 프로모션이 적용되는 달력상 기간. 시작일과 종료일을 모두 포함한다. 적용 여부는 예약 생성 시점이 이 기간 안인지로 판정한다. 숙박 기간과 포함 규칙이 다르다 |
| 할인 배분 | Allocation | 할인 총액을 숙박 날짜별 단가에 비례해 나눠 금액 스냅샷에 날짜별로 기록하는 것. 배분액의 합은 할인 총액과 정확히 일치해야 한다. 단수는 날짜별 비례 내림 후 마지막 날짜 행에 가산한다 |
| 상태 | OPEN, CLOSED | 프로모션의 두 상태. CLOSED는 다시 열리지 않는다 |
| 생성 | Create | 없던 프로모션을 새로 만드는 것 |
| 종료 | Close | 더 이상 적용되지 않게 닫는 것. 삭제가 아니다. 종료된 프로모션은 수정할 수 없다 |

캠페인 기간과 숙박 기간을 반드시 갈라 쓴다. 9월에 파는 12월 숙박 상품에 붙는 할인이라면 캠페인 기간은 9월이고 숙박 기간은 12월이다. 생성 후 캠페인이 끝나도 이미 만든 예약의 할인은 유지된다(R5).

## 5. 예약 용어 (2026-09-08 v11: 확정 우선 추가)

| 한국어 | 영문 | 정의 |
|---|---|---|
| 예약 | Booking | 이용자가 특정 객실 타입을 특정 기간 묵겠다고 만든 계약. 생성 시점부터 재고를 붙잡는다 |
| 선점 중 | HELD | 생성됐고 결제가 끝나지 않은 상태. 재고를 임시로 붙잡고 있고 TTL이 돈다 |
| TTL | ttl | HELD가 유지되는 시간. 값은 설정 파라미터 (기본 10분 [가설], Step 9) |
| 확정 | CONFIRMED | 결제 승인으로 예약이 성립한 상태 |
| 취소 | CANCELED | 확정된 예약을 이용자가 무른 상태 |
| 만료 | EXPIRED | TTL 만료 또는 결제 실패 한도 도달로 HELD가 종료된 상태. 붙잡았던 재고는 반환된다 |
| 만료시키기 | ExpireBooking(reason) | HELD 예약을 EXPIRED로 보내는 커맨드. reason은 TTL_EXPIRED 또는 PAYMENT_FAILED. 이미 EXPIRED면 재호출 무해 |
| 확정 우선 | Confirm-First | TTL에 도달한 HELD를 처리할 때 미정산 승인 결제가 있으면 만료시키지 않고 확정하는 규칙. 판정 기준은 먼저 발생이 아니라 먼저 커밋이다. 스케줄러가 몇 밀리초 먼저 돌았다는 이유로 승인된 결제의 예약을 날리지 않는다 (v11 추가, 08-3 결정 11-1) |
| 체크인 | checkIn | 숙박이 시작되는 날. 이 날부터 재고를 점유한다 |
| 체크아웃 | checkOut | 숙박이 끝나는 날. 이 날은 재고를 점유하지 않는다 |
| 숙박 기간 | StayPeriod | 체크인부터 체크아웃까지. 박수는 두 날짜의 차이 |
| 연박 | Multi-night | 박수가 2 이상 |
| 인원 | userCount | 묵는 사람 수. 신청 시점의 maxOccupancy를 넘을 수 없다 |
| 이용자 식별자 | userId | 예약을 만든 이용자. v1에서 Booking이 가진 유일한 이용자 정보 |
| 금액 스냅샷 | PriceSnapshot | 생성 시점의 날짜별 단가와 할인 배분액, 적용 프로모션 식별자와 이름, 총액을 복사해 보관한 것. 결제 청구액의 근거이며 총액은 저장값이다 |
| 날짜별 가격 행 | DailyPrice | PriceSnapshot 안의 날짜 하나. 그날의 단가와 할인 배분액 |
| 멱등키 | idempotencyKey | 같은 요청이 반복돼도 예약이 하나만 생기게 하는 식별자. 같은 키의 재요청은 기존 예약을 반환한다 |

상태 전이는 HELD에서 CONFIRMED로, HELD에서 EXPIRED로, CONFIRMED에서 CANCELED로 셋뿐이다. CONFIRMED에서 EXPIRED로는 없다.

## 6. 결제 용어 (2026-09-08 v11: 정산 표식, 고아 승인, 시도 식별자, 환불 멱등키 추가)

| 한국어 | 영문 | 정의 |
|---|---|---|
| 승인 | Approved | PG가 결제를 성공 처리한 것 |
| 실패 | Failed | PG가 결제를 거절한 것 |
| 환불 | Refunded | 승인된 결제를 되돌린 것 |
| 콜백 | Callback | PG가 결과를 우리에게 통보하는 호출 |
| 청구액 | Amount | PG에 청구한 실제 금액. 예약이 실어 보낸 스냅샷 총액과 일치해야 한다 |
| 결제 시도 | PaymentAttempt | Payment 안의 하위 엔티티. 한 번의 PG 요청과 그 결과. FAILED 이후의 재시도는 상태 역행이 아니라 새 시도 생성이다 |
| 시도 종류 | kind | 결제 시도 행의 종류. NORMAL은 정상 요청에서 나온 시도이고 ORPHAN은 고아 승인을 기록한 행이다. 시도 상한, 승인 유일, 진행 유일 세 규칙은 NORMAL만 센다 (v11 추가) |
| 시도 식별자 | attemptId | 시도를 열 때 발급하는 식별자. 콜백이 어느 시도의 결과인지 가리키고, 정상 환불의 PG 멱등키로도 쓰인다. NORMAL 시도에만 있다 (v11 추가) |
| 정산 표식 | Settlement Mark (settledAt, settledBy) | 예약 컨텍스트가 이 결제를 보고 할 후속(확정, 만료, 환불)이 현재 없다는 표식. 단위는 결제 한 건이다. 예약 컨텍스트가 결제 상태를 읽고 분기를 끝낸 트랜잭션은 결과가 무엇이든 이 표식을 찍고 끝난다. 결제 컨텍스트가 승인을 기록하거나 3회째 실패를 기록하면 표식을 되돌린다. settledBy는 누가 찍었는지를 남기는 관측용 값이고 분기에 쓰지 않는다 (v11 추가) |
| 고아 승인 | Orphan Approval | 예약이 기다리지 않는 승인. 셋이다. 이미 종착인 시도에 온 승인, 이미 승인 이력이 있는데 온 승인, 금액이 청구액과 다른 승인. 별도 요소가 아니라 kind가 ORPHAN인 시도 행으로 기록되고 즉시 환불된다 (v11 추가) |
| 환불 대기 | REFUND_PENDING | 고아 승인의 환불이 실패해 남은 상태. 순찰 정책이 재시도한다 (v11 추가) |
| 환불 멱등키 | Refund Idempotency Key | PG 환불 재요청이 이중 환불이 되지 않게 하는 키. 새로 발급하지 않고 기존 식별자에서 유도한다. 정상 환불은 그 시도의 attemptId, 고아 환불은 그 고아의 pgTransactionId다. 유도 키라서 트랜잭션이 롤백돼도 재시도가 같은 키를 쓴다 (v11 추가) |
| 결제 상태 | PaymentStatus | 시도의 상태다. NORMAL은 REQUESTED에서 APPROVED 또는 FAILED로, APPROVED에서 REFUNDED로만 전이한다. ORPHAN은 REFUND_PENDING에서 REFUNDED로만 전이한다. Payment 자체는 저장 상태 없이 시도 목록에서 계산한다 |
| 결제 시도 횟수 | attemptCount | 이 예약에 대한 NORMAL 시도 누적 수. 3을 넘을 수 없다. 저장하지 않고 시도 목록에서 계산한다 |
| 거래 식별자 | pgTransactionId | PG가 발급한 거래 번호. 같은 번호의 콜백이 다시 오면 승인이든 실패든 무시한다. NORMAL과 ORPHAN을 통틀어 유일하다 |

## 7. 정책 용어 (2026-09-08 v11 신설)

정책은 도메인 개념이 아니라 자동 반응 규칙이지만, 문서 사이에서 같은 이름으로 불려야 해서 여기 둔다.

| 한국어 | 영문 | 정의 |
|---|---|---|
| 순찰 정책 | Patrol Policy (T2) | 정산 표식이 없는 결제와 환불 대기 고아를 주기적으로 찾아 후속을 마무리하는 시간 트리거 정책. 이벤트 유실을 보정하는 유일한 수단이다 |
| TTL 만료 정책 | T1 | 기한이 지난 선점 중 예약을 찾아 확정 우선 규칙으로 확정하거나 만료시키는 시간 트리거 정책 |
| 임계 | threshold | 순찰 정책이 후보로 집기까지 기다리는 시간. 정상 처리가 끝날 시간을 준다. 임계는 순찰 주기보다 짧고 순찰 주기는 TTL보다 짧다 |
| 후보 기준 시각 | candidateSince | 순찰 후보를 정렬하는 키. 오래된 것부터 처리해 굶주림을 막는다 |

## 8. v1 범위 밖

- 회원: 이용자는 userId로만 식별
- 쿠폰: 전체
- 호실 배정: 객실 타입까지만
- 알림, 정산, 리뷰
- 호스트나 운영자에 의한 예약 취소
- 프로모션 자동 종료
- 다중 객실 예약: 예약 한 건의 객실 수는 1이다
- 부분 환불: 환불은 전액이다

## 9. 서비스 이름 후보 (2026-09-08 v11: PaymentApplicationService 추가)

애그리거트가 아닌 조율자들의 이름 후보다. 도메인 용어는 아니지만 문서 간 교차 참조를 위해 여기 둔다.

| 이름 후보 | 성격 | 소속 | 책임 요약 |
|---|---|---|---|
| InventoryAllocationService | 도메인 서비스 | 재고와 요금 | 연박 N행에 hold, commit, release를 원자적으로 적용 |
| InventoryApplicationService | 앱 서비스 | 재고와 요금 | 개설 N행 생성, 조정, roomTypeId 존재 확인 |
| BookingApplicationService | 앱 서비스 | 예약 | 트랜잭션 경계. 재고와 결제 호출, RequestPayment 중계, 상태에 따른 분기 선택, T1과 T2 진입점 |
| PaymentApplicationService | 앱 서비스 | 결제 | PG 호출, 고아 환불, 환불 멱등키 유도, 예약에 조회 API 제공. 애그리거트 대신 외부와 말하는 유일한 자리다 (v11 추가) |
| PricingService | 도메인 서비스 | 예약 [가설] | 단가와 프로모션을 읽어 DailyPrice 행과 할인 배분 계산 |
