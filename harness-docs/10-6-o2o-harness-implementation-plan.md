# O2O 하네스 실제 적용과 서비스 구현 계획

작성: 2026-09-07
최종 갱신: 2026-09-07 v2
상태: 작업 분해 초안. 실제 구현과 테스트는 아직 수행하지 않았다.
기준: 실행 결정 v4, 작업 인계 v2, 설계 계획 v9와 API 명세 v2

API 작업 입력: [11-o2o-api-spec.md](C:/Dev/potenup/99_projects/o2o/11-o2o-api-spec.md). 기능별 요청과 응답, 오류, 멱등 처리와 계약 테스트를 연결한다. 해당 명세의 P01~P11은 제안값이며 확정 전제로 자동 편입하지 않는다.

하네스 기획의 범위를 설계 문서 운영에서 실제 적용과 O2O 서비스 구현 계획까지 확장한다. 이번 범위는 로컬 환경의 개발과 최종 검증까지이며 배포와 운영 준비는 사용자 요청에 따라 제외한다. 기존 다섯 필수 항목의 세부 작업은 일반 글씨로 적었다. 별도로 추가한 단계와 보완 항목은 기울임으로 표시했다. 추가 항목은 이번 계획의 제안이며, 미결인 설계를 확정한 것으로 해석하지 않는다.

## 1. 범위와 기술 구성

현재 기술 구상은 Spring 기반 Java 백엔드, Next.js 프론트, MySQL이다. 개발과 수정은 Claude Code, 평가는 Codex에서 수행하고 사용자가 결과를 전달한다. 별도 LLM API 호출과 과금은 사용하지 않는다.

로컬 문서 기준으로 단일 Spring Boot 모듈과 컨텍스트별 패키지 분리를 전제로 한다. 결제와 환불은 Mock이고, 회원 기능, 쿠폰, 알림, 정산, 리뷰는 v1 제외다. 최신 원본과 다르면 구현 전에 차이를 정리한다.

## 2. 세부 작업 목록

### A. *요구사항과 구현 계약 정리*

- *사용할 01과 실제 평가 기준을 연결하고 버전 차이를 정리한다. 07을 적용하는 설계 Task에서는 해당 원문도 확보한다.*
- *v1 포함 기능, 제외 기능, 보류 기능을 구분한다. 취소 수수료, 판매 제약, 검색 금액과 예약 금액 차이, 부분 취소와 예약 변경의 처리 범위를 명시한다.*
- *예약과 재고의 트랜잭션 범위, 동시성 제어 방식, Payment 식별 단위를 구현 전에 확정한다.*
- *화면별 사용 흐름과 API의 요청, 응답, 오류, 상태 전이를 정의한다.*
- *날짜와 시간대, 금액 표현, 멱등키, 페이지 조회 규칙을 프론트와 백엔드가 공유한다.*
- *기능별 인수 조건을 작성하고 요구사항, 구현 위치, 테스트를 연결한다.*

완료 기준: 첫 구현 기능에 필요한 계약과 입력 버전이 정리돼 있고, 미결 사항이 구현 코드에 임의로 들어가지 않는다.

### B. 초기 세팅

- 저장소와 작업 브랜치, 문서, 백엔드, 프론트, 테스트 결과 폴더 구조를 구성한다.
- Java, Spring Boot, Node.js, Next.js, MySQL의 사용할 버전을 확인하고 고정한다.
- Spring 프로젝트를 생성하고 컨텍스트별 패키지, 빌드, 테스트 실행 구성을 만든다.
- Next.js 프로젝트를 생성하고 라우팅, 공통 레이아웃, 코드 검사, 빌드 구성을 만든다.
- 개발용 MySQL을 구성하고 계정, 연결 정보, 문자셋과 시간대 설정을 확인한다.
- 개발 환경과 테스트 환경의 설정 및 데이터를 분리한다.
- 백엔드 실행, 프론트 실행, DB 연결을 각각 확인하고 재현 명령을 기록한다.
- *비밀 값이 없는 환경변수 예시와 저장소 제외 규칙을 작성한다.*
- *스키마 변경 이력과 초기 테스트 데이터 관리 방식을 마련한다.*
- *CLAUDE.md와 AGENTS.md에 공통 기술 전제, 실행 명령, 변경 범위, 완료 기준을 일치시킨다.*

완료 기준: 새 작업 환경에서 문서에 적힌 순서대로 실행해 프론트, 백엔드, DB를 확인할 수 있다.

### C. *하네스 실제 적용과 구현 작업용 보완*

- *첫 적용 기능을 작게 정하고 입력, 변경 허용 파일, 완료 기준을 작성한다.*
- *보완한 생성, 평가와 반영 양식에 코드 변경, 테스트 명령과 결과 경로를 채워 첫 Task에 적용한다.*
- *코드 평가용 기준을 마련한다. 기존 DDD 평가 축만으로 프론트, 보안, 테스트 품질까지 검증됐다고 보지 않는다.*
- *코드 작업의 형식 검사는 빌드, 테스트, 코드 검사와 변경 범위 확인으로 정의한다. 설계 문서의 G1 형식을 코드에 그대로 적용하지 않는다.*
- *Claude Code에서 구현과 테스트를 수행하고 변경 파일, diff, 실행 결과, 남은 문제를 저장한다.*
- *Codex의 새 작업에 01 전체, 승인한 기능 계약, 평가 대상 코드, 허용한 의존 파일과 테스트를 전달한다. 이전 평가나 생성 대화를 예시로 넣지 않는다.*
- *평가자가 실행할 명령과 테스트 데이터 범위를 명시하고, 직접 확인한 결과와 전달받은 결과를 구분해 기록한다.*
- *사용자가 평가를 판단하고 Claude Code가 수용 항목을 수정한다. 재평가는 최대 1회로 유지한다.*
- *최종 변경본의 테스트와 diff를 확인하고 사용자 승인, 실제 사용 시간, 중단 시 재개 위치를 기록한다.*

완료 기준: 첫 기능에서 생성, 테스트, 평가, 사용자 결정, 수정, 최종 검증까지 수동 전달이 실제로 이어진다. 아직 원본이 없는 평가 기준을 검증된 기준처럼 사용하지 않는다.

### D. 백엔드 개발과 테스트 코드

#### D-1. 공통 기반

- 컨텍스트별 도메인 모델과 JPA 엔티티, 값 객체, Repository를 구현한다.
- 테이블, 제약조건, 인덱스, 스키마 변경 파일을 작성한다.
- 요청 검증, 공통 오류 응답, 상태 코드와 예외 처리를 구현한다.
- 트랜잭션 경계와 컨텍스트 간 호출 계약을 구현한다.
- *회원 기능 제외 전제에 맞춰 게스트와 호스트 식별 방법 및 데이터 접근 범위를 정한다. 클라이언트가 보낸 guestId만으로 소유권 검사가 끝났다고 보지 않는다.*

#### D-2. 기능 구현

- 숙소와 객실 타입 등록, 수정, 조회를 구현한다.
- 날짜별 재고와 요금 등록, 수정, 조회를 구현한다. 기간 일괄 등록은 재고에 적용한다.
- 자동 적용형 프로모션과 금액 계산을 구현한다.
- 지역, 날짜, 인원 검색과 연박 가용성 및 예상 금액 조회를 구현한다.
- 예약 요청, 멱등 처리, 연박 재고 선점, 생성 시 금액 스냅샷 저장을 구현한다.
- Mock 결제 요청, 성공, 실패, 재시도, 중복 승인 처리를 구현한다.
- 예약 확정, 목록, 상세, 취소, Mock 환불과 재고 반환을 구현한다.
- HELD 예약의 TTL 만료와 결제 실패 한도 도달 처리를 구현한다.

#### D-3. 테스트 코드

- 도메인 단위 테스트: 금액 계산, 불변식, 상태 전이와 선행조건을 검증한다.
- 서비스 테스트: 예약, 결제, 재고 조율과 실패 시 처리를 검증한다.
- Repository 테스트: MySQL에서 매핑, 조회, 유니크 제약과 트랜잭션 롤백을 검증한다.
- API 테스트: 정상 요청, 입력 오류, 존재하지 않는 자원, 허용하지 않은 접근을 검증한다.
- 동시성 테스트: 마지막 재고 경쟁, 중복 예약 요청, 연박 중 일부 날짜 부족을 검증한다.
- 결제 테스트: 진행 중인 중복 요청, 승인 중복, 3회 실패와 지연 승인을 검증한다.
- 시간과 정책 테스트: TTL 경계, 만료와 승인 경합, 중복 만료와 중복 재고 반환을 검증한다.
- 구조 테스트: 컨텍스트 간 의존과 애그리거트 경계를 검증한다.
- *테스트에서 시간과 Mock 응답을 제어하고, 테스트 종료 시 데이터를 정리해 반복 실행 결과를 안정화한다.*

완료 기준: 해당 기능의 정상 흐름과 핵심 실패 조건을 테스트로 확인하고, 실행 명령과 결과가 코드 버전에 연결된다.

### E. 프론트 개발

- 라우팅, 공통 레이아웃, 입력 폼, 공통 컴포넌트를 구성한다.
- 숙소 검색, 검색 결과, 숙소와 객실 상세 화면을 구현한다.
- 숙박 날짜와 인원 선택, 가용성, 예상 금액 표시를 구현한다.
- 예약 요청, Mock 결제, 실패 안내, 재시도 화면을 구현한다.
- 예약 목록, 상세, 상태 표시와 취소 화면을 구현한다.
- 판매 준비용 숙소, 객실, 재고, 요금과 프로모션 관리 화면을 구현한다.
- 공통 API 호출, 응답 변환, 오류 표시와 서버 데이터 갱신을 구현한다.
- 로딩, 빈 결과, 입력 오류, 재고 소진, 만료와 네트워크 실패 상태를 처리한다.
- 중복 클릭, 새로고침, 뒤로 가기와 오래된 화면 데이터 처리를 확인한다.
- 결제 202 접수 이후 상태를 조회하고, 같은 요청 재전송과 명시적인 다음 결제 시도의 멱등키를 구분한다.
- PRICE_CHANGED 응답 시 금액을 다시 조회해 확인받고, 만료 상태는 서버 시각과 예약 조회로 갱신한다.
- 컴포넌트와 폼 동작 테스트를 작성하고 타입 검사 및 빌드를 확인한다.
- *모바일 화면, 키보드 조작, 입력 항목 이름과 오류 안내의 접근성을 확인한다.*

완료 기준: 화면에서 해당 기능을 수행할 수 있고, 실패 상태에서 사용자가 다음 행동을 알 수 있다.

### F. 연결 테스트

- Next.js에서 Spring API를 호출하고 MySQL에 저장된 결과까지 확인한다.
- API 주소, 프록시 또는 CORS 설정, 필요한 식별 정보의 전달을 확인한다.
- 요청과 응답의 필드, 오류 코드, 날짜, 시간대, 금액이 계약과 일치하는지 확인한다.
- 검색, 객실 선택, 예약, Mock 결제, 확정, 예약 조회를 브라우저에서 연속 실행한다.
- 예약 취소, Mock 환불, 재고 반환을 브라우저와 DB에서 함께 확인한다.
- 결제 실패와 재시도, TTL 만료, 지연 승인 시 화면과 서버 상태가 일치하는지 확인한다.
- 타임아웃, 요청 재전송, 중복 클릭과 새로고침 후에도 예약이나 결제가 중복되지 않는지 확인한다.
- 핵심 사용자 흐름의 브라우저 자동 테스트를 구성한다.
- *테스트용 데이터와 Mock 실패 조건을 공유해 동일한 연결 오류를 재현할 수 있게 한다.*

완료 기준: 화면에 표시된 결과와 서버 및 DB 상태가 일치하고, 정상 및 실패 흐름이 재현된다.

### G. 검증

- 요구사항별로 구현과 테스트 누락을 대조한다.
- 초과 예약 0, 연박 선점 전체 성공 또는 전체 실패, 중복 예약 방지를 확인한다.
- 예약당 승인 결제 하나, 금액 스냅샷 불변, HELD 종료 시 재고 반환을 확인한다.
- 변경한 기능과 영향받는 기존 기능의 테스트를 실행한다.
- 백엔드와 프론트 빌드, 타입 검사, 코드 검사와 구조 검사를 확인한다.
- Codex 평가 지적과 사용자 결정이 최종 코드에 맞게 반영됐는지 확인한다.
- 수용하지 않은 내용의 변경 여부와 최종 diff를 확인한다.
- 실제 치명 결함과 오판 정정을 구분하고, 오판에는 근거, 대안, 안티패턴을 남긴다.
- *데이터 접근 통제, 입력 검증과 로그에 민감정보가 남는지 확인한다.*
- *조회 쿼리, 인덱스, 동시 요청 시 응답 시간과 DB 락 경합을 측정한다. 합격 기준은 측정할 부하 조건과 함께 정한다.*
- *버그를 수정할 때 같은 오류를 다시 잡을 회귀 테스트를 추가한다.*

완료 기준: 최종 코드 버전에 대한 검증 근거가 있고, 미해결 사항을 기록한 뒤 사용자가 완료를 승인한다. 평가가 끝났다는 사실만으로 테스트 통과를 대신하지 않는다.

## 3. 실행 순서

이 목록은 업무 분류다. 백엔드 전체를 끝낸 뒤 프론트 전체를 시작하는 순서로 고정하지 않는다. 선행 계약과 환경을 준비한 뒤 기능 하나마다 백엔드와 테스트, 프론트, 연결 테스트, 검증을 반복한다.

1. *최신 원본과 첫 기능의 계약을 정리한다.*
2. 초기 세팅을 완료한다.
3. *숙소 조회처럼 범위가 작은 기능으로 하네스 전달 흐름을 먼저 검증한다.*
4. 판매 준비, 프로모션, 검색, 예약과 재고 선점, Mock 결제와 확정, 취소와 만료 순으로 기능을 확장한다.
5. 각 기능에서 백엔드와 테스트, 프론트, 연결 테스트, 최종 검증을 수행한다.
6. 전체 흐름과 최종 변경본을 검증하고 완료 현황, 미해결 사항과 다음 작업을 기록한다.

첫 적용 기능은 제안 상태다. 개발 중 고정할 기술 버전이나 미결 도메인 정책을 이미 확정한 것으로 취급하지 않는다. 업무별 시간은 실제 수행 시간을 기록하며 보완한다.

### 기능별 API와 검증 연결

| 구현 묶음 | API ID 또는 내부 처리 | 주요 검증 ID |
|---|---|---|
| 숙소와 객실 | CAT-01~09 | T01, T02 |
| 재고와 요금 | INV-01~05, RATE-01~04 | T03~T07 |
| 프로모션과 검색 | PROMO-01~05, SEARCH-01~03 | T12, T13, T27, T28 |
| 예약과 선점 | BOOK-01~03, HoldInventory | T08~T13, T29 |
| 결제와 확정 | PAY-01~02, INTERNAL-01, ConfirmBooking | T14~T23, T26 |
| 취소와 만료 | BOOK-04, ExpireBooking, RefundPayment | T17~T25 |
| 접근 범위 | 로컬 행위자, 소유권과 Mock 경로 | T02, T30 |

각 묶음에서 백엔드 테스트와 프론트 연결을 함께 확인한다. 아직 테스트 코드가 작성됐다는 의미는 아니다. 첫 Task는 숙소 등록과 조회처럼 작은 범위에서 시작하고 변경 대상 API와 검사 항목을 작업 계약에 적는다.

## 4. 작업별 기록

- 작업 ID와 목표, 선행 작업
- 입력 파일과 버전, 승인한 계약
- 변경 허용 범위와 예상 산출물
- 실행한 테스트 명령과 결과, 실행하지 못한 검증
- 평가 리포트, 사용자 결정과 수정 내역
- 최종 코드 버전, 완료 기준 충족 여부와 사용자 승인
- 실제 사용 시간, 중단 위치와 다음 작업

현재 문서와 코드 작업 양식, API 명세와 작업 분해를 작성했다. 남은 작업은 입력 버전과 실제 평가 기준 확정, 첫 Task 작성, 실제 하네스 적용, 서비스 구현과 테스트다.
