### 1-2. 10-4의 "01 전체 제공"은 스킬 원본과 정면 충돌한다

10-4 v4 1절: "평가 입력 01: 확정 전제 표만 추출하지 않고 문서 전체를 제공한다." 3절: "평가 입력에서 01 차단: 폐기. 01 전체를 허용."
스킬 원본 1절: "계획 문서를 통째로 넘기면 안 된다. 배경이 필요하면 쟁점과 권고를 제거한 입력 팩을 쓴다. 입력 팩이 없으면 먼저 만든다. 편의상 통째로 던지는 것이 이 스킬을 무력화하는 유일한 방법이다." 7절 하지 말 것 첫 항목: "계획 문서나 쟁점 문서를 통째로 서브에이전트에게 넘기기."
입력 팩 0절: "그 문서 3장과 4장에는 쟁점에 대한 권고와 근거가 들어 있고, 그걸 읽은 에이전트는 권고를 정당화하는 방향으로만 판정한다."

10-4의 결정은 스킬 원본과 입력 팩이 미확보인 상태에서 내려졌다(10-5 2절). 이제 둘 다 있으므로 재검토 대상이다. 10-4 4절이 "폴더와 프롬프트 지시는 입력 혼입을 줄이는 운영 규칙이다. 강제 차단을 보장하지는 않는다"라고 스스로 적었듯이, 수동 실행에서는 입력 목록이 유일한 차단 수단이다. 그 목록에 01 전체를 넣으면 남는 차단이 없다. 06-3, 06-5, 08-1의 실적은 전부 입력 팩 방식이었다. 권고는 입력 팩(08-3 수용 뒤 v3)이다. 사용자 결정.

### 1-3. 내 프로젝트 문서 번호 충돌

직전 세션에서 프로젝트에 저장한 10-3(PDF 대조)과 10-4(템플릿 대조)가 로컬 번호와 충돌했다. 10-3은 10-7로 옮기고 정정 주석을 달았다. 구 10-4는 이 문서로 대체하고 프로젝트에서 삭제했다.

준비 작업은 지금 시작할 수 있다. 10-5 8절의 남은 준비 5개 중 셋(01 버전, 07, 평가 기준)은 결정이 아니라 확보 문제였고 6절 파일로 해소됐다. 첫 Task 실행 전에 남는 사용자 결정은 셋이다.

1. 설계 계열 병합 방향(1-1). 이것이 정해져야 입력 팩 v3, 07 v3, 11 v3의 기준이 생긴다.
2. 평가 입력을 01 전체로 할지 입력 팩으로 할지(1-2).
3. 08-3 8절 사용자 결정 11개. Step 9와 11 v3의 전제다.

셋 다 코드 없이 결정할 수 있다. 결정 뒤 5절 순서로 들어간다.

## 5. 하네스 설계 과정 (수동 실행 기준)

수동 실행에서 하네스는 프로그램이 아니라 파일 규약, 검사 스크립트, 기록 규칙의 묶음이다. LLM 호출은 사람이 두 앱에서 한다. 그래서 설계 순서는 원본 정렬 → 파일 레이아웃 → 평가 기준 → 검사 스크립트 → 기록 규칙 → 첫 Task다.

### 5-1. 원본 정렬

프로젝트 계열 문서를 로컬로 가져와 병합한다. 이번 세션에서 3개(01 v19, 07 v2, 입력 팩 v2)를 project-sync/에 넣었다. 나머지 15개(04-5, 04-6, 05-1, 05-2, 05-3, 06-1, 06-2와 설명, 06-3, 06-4와 설명, 06-5, 06-6, 08-1, 08-2, 08-3, 09, 09-1)는 병합 결정 뒤 같은 방식으로 가져온다. 병합 결과가 01 v20이고, 로컬 05 v7과 프로젝트 05-3 v10의 용어 충돌은 병합 시 표로 남긴다.

### 5-2. 파일 레이아웃

로컬 폴더 기준. 새 디렉터리는 4개다.

```
o2o/
  01~12, o2o-*.md           확정본
  harness-prompts/           양식 5종 + eval-criteria-ddd.md + (코드용 기준) + 07 v3
  tasks/task-S9.md           채워진 작업 계약. 승인 기록 포함
  out/task-S9-R1/            후보. generate 응답, 형식 보정 이력
  reviews/task-S9-R1-A.md    Codex 리포트 원문. -B.md
  decisions/task-S9-R1.md    결정표. 오판 기록 포함
  state/progress.md          추가 기록 전용. 행 형식은 3-1 마지막 행
  project-sync/              프로젝트 계열 원본 사본. 병합 뒤 삭제 또는 보관
  tmp/                       정리 대상. check.mjs는 harness-prompts/tools/로
```

파일명에 Task, 라운드, A/B가 들어가야 G2가 버전 일치를 파일명만으로 1차 검사할 수 있다.

### 5-3. 평가 기준

설계 문서용은 6절의 eval-criteria-ddd.md로 확보됐다. 코드용은 없다. 10-6 C가 "기존 DDD 평가 축만으로 프론트, 보안, 테스트 품질까지 검증됐다고 보지 않는다"고 적은 대로 별도 파일이 필요하다. 축 후보는 10-6 D-3 테스트 항목과 G 검증 항목에서 뽑는다(경계 위반, Repository 단위, 계약 하강, 레이어 역전은 스킬 Step 9 축 그대로. 추가로 API 계약 준수, 멱등 규칙, 소유권 검사, 테스트 격리). 심각도 정의와 출력 스키마는 설계용과 같은 것을 쓴다. 이것은 첫 코드 Task 전에 초안이 있어야 하고, 첫 Task의 리포트로 검증한다.

### 5-4. 검사 스크립트

check.mjs를 확장한다. Node를 유지하는 이유는 tmp/document-review/check.mjs와 tmp/api-spec-v2/build-v2.mjs가 이미 Node이기 때문이다. 세 명령이면 된다.

| 명령 | 검사 | 실패 시 |
|---|---|---|
| check fill <양식> | {{...}} 잔존 0개. 경로가 절대경로이고 존재. 버전 칸에 sha256 자동 기입 | 잔존 빈칸 목록 출력 |
| check g1 <후보> --type doc\|api\|code | doc: 승인 양식 필수 항목, 날짜, 금지 기호(볼드, 긴 줄표, 가운뎃점), 종료 문장. api: 요청 응답 오류 절과 내부 링크. code: 빌드와 테스트 명령 실행 결과 파일 존재 | 검사 이름, 위치, 메시지 목록. 이 목록이 재요청 프롬프트에 들어간다 |
| check g2 <결정표> | 대상, 계약, A, B 버전 일치. A와 B 지적 ID 집합 = 결정표 ID 집합. 행 수 = A + B. 빈 결정 없음. 거부에 이유. 반박은 확인필요만. 치명 거부에 오판 기록 필수 필드. 남은 실제 치명 0 | 항목별 통과와 실패. 결과를 decision-table.md의 G2 확인 절에 붙이고 사람이 서명 |

세 명령 모두 LLM을 부르지 않는다. 10-4 3절의 "로컬 검사 도구" 그대로다.

### 5-5. 기록 규칙

state/progress.md 한 행의 필드: Task, 라운드, 단계(계약, 생성, G1, 평가 A, 평가 B, 결정, G2, 반영, 최종), 결과, 실패 원인, 교훈, 다음 작업, 실제 시간. 10-4 6절의 시간 기록과 10-5 7절의 재개 정보가 이 한 행에 들어간다. 재요청과 재평가 프롬프트에 넣는 실패 사유의 원천은 이 파일이다.

status 값은 10-2의 pending, drafted, reviewed, applied, done, halted를 유지하되 사람이 progress.md에 적는다. done은 사용자 최종 승인 행에서만 바뀐다.

### 5-6. 첫 Task 순서

10-6 3절은 숙소 조회(코드)로 전달 흐름을 먼저 검증하자고 한다. 순서를 바꾸는 편이 맞다.

1. 08-3 8절 결정 11개. 사용자.
2. Step 9 설계 문서 Task를 하네스 첫 바퀴로 돈다. 이유 셋. 설계 문서용 평가 기준은 확보됐고 코드용은 없다. Step 9 산출물(패키지 구조, 저장 모델, 계약표의 테스트 변환)이 없으면 첫 코드 Task의 변경 허용 파일과 완료 기준을 쓸 수 없다. 10-6 A의 완료 기준 "미결 사항이 구현 코드에 임의로 들어가지 않는다"를 지키려면 미결이 문서에서 먼저 닫혀야 한다.
3. 11 API v3 대조(3-3).
4. 첫 코드 Task: 숙소 등록과 조회(CAT-01, 03, 04. T01, T02). 10-6 3절 3항과 같다.

### 5-7. 회고

Task마다 progress.md의 실제 시간과 실패 원인을 모아 10-4 6절의 시간 기준을 정한다. 같은 실패 원인이 두 번 나오면 07 v3 DO NOT 블록에 한 줄 추가한다(10-7 2-1).
