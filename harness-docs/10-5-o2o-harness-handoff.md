# O2O 하네스 작업 인계

최초 작성: 2026-09-07
최종 갱신: 2026-09-07 v2
기준: 실행 결정 v4, API 명세 v2
상태: 문서와 코드 작업 양식 정리. 실제 하네스 적용과 서비스 구현은 미실행.

## 1. 작업 방식

- 생성과 수정은 Claude Code에서 수행한다.
- 평가는 Codex의 새 작업에서 A와 B를 분리해 수행한다. A와 B는 같은 대상 버전을 평가하고 서로의 결과를 읽지 않는다.
- 사용자가 파일을 전달하고 지적별 결정 및 최종 승인을 남긴다.
- 별도 LLM API 호출과 앱 간 자동 호출은 사용하지 않는다. 로컬 서비스 API 테스트는 허용한다.
- 평가에는 01 전체를 제공한다. 과거 평가 지적과 해답을 예시로 넣지 않는다.
- 재평가는 최대 1회이며 최초 R1, 재평가 R2로 표시한다. 횟수 소진은 완료 근거가 아니다.
- 개발 범위는 Next.js, Spring 기반 Java, MySQL의 로컬 개발과 검증까지다. 배포와 운영 준비는 제외한다.

## 2. 작업 입력

| 자료 | 용도 | 현재 상태 |
|---|---|---|
| 01 설계 계획 | 도메인 전제와 미결 설계 | 로컬 v8을 보완한 v9. 기존 계획의 v19는 미확보 |
| 02~06 설계 문서 | 기능, 이벤트, 책임, 용어와 보드 범례 | 필요한 파일을 Task 입력에 지정 |
| 10-4 실행 결정 | 역할, 비용, 평가와 완료 정책 | v4 |
| 10-6 구현 계획 | 초기 세팅부터 최종 검증까지의 작업 분해 | API ID와 검증 항목 연결 |
| 11 API 명세 | 요청, 응답, 오류와 내부 정책 | 독립적인 v2 초안. P01~P11은 제안 |
| 07 생성 마스터 원본 | 해당 원본을 사용하는 설계 Step의 생성 규칙 | O2O 원본 미확보 |
| 실제 평가 기준 | 평가 축, 심각도와 리포트 스키마 | 기존 ddd-blind-review 원본 미확보. 코드용 기준도 확정 필요 |
| 이번 Task 계약 | 입력, 변경 범위, 정책과 완료 기준 | 작업마다 작성 필요 |

기준 문서가 없는 부분을 임의로 복원하지 않는다. 07 원문에 의존하는 설계 작업은 해당 원문을 확보해야 한다. 제공된 독립 양식으로 수행하는 API 또는 코드 작업에는 적용 규칙을 Task에 명시한다. 이를 기존 07이나 DDD 평가 스킬과 동등하다고 간주하지 않는다.

## 3. 사용할 양식

| 양식 | 작성 내용 |
|---|---|
| harness-prompts/task-contract.md | 작업 유형, API ID, 정책 선택, 입력 버전, 허용 변경과 검사 |
| harness-prompts/generate.md | 문서 생성 또는 코드 구현 요청 |
| harness-prompts/evaluate.md | A 또는 B 평가 요청과 코드 실행 범위 |
| harness-prompts/decision-table.md | 지적별 사용자 결정과 오판 판단 |
| harness-prompts/apply.md | 수용한 변경 반영과 최종 검사 |

모든 양식의 필수 빈칸을 실제 값으로 채운다. 파일 경로는 절대경로로 적는다. 사용하지 않는 선택 항목은 없음으로 표시한다.

## 4. 앱별 전달 자료

| 단계 | 전달할 자료 | 남길 결과 |
|---|---|---|
| Claude Code 생성 | 생성 요청, Task 계약, 실행 결정, 01 전체, 적용 양식과 API, 필요한 입력 | 문서 후보 또는 코드 diff, 검사 결과, 입력과 출력 버전 |
| Codex 평가 | 평가 요청, Task 계약, 01 전체, 동일 버전의 대상과 허용 의존 파일, 실제 평가 기준 | A 또는 B 리포트, 직접 확인한 근거와 미검증 항목 |
| 사용자 결정 | A와 B 원본, 결정표, 평가받은 버전 | 수용, 거부, 반박과 필요한 오판 기록 |
| Claude Code 반영 | 반영 요청, 동일 대상 버전, 원본 리포트, 사용자 결정과 관련 입력 | 수정 후보, 지적별 변경 위치, 최종 diff와 검사 결과 |

평가자는 생성 대화, 다른 평가 리포트, 사용자 결정표와 별도의 하네스 검토 기록을 입력에 자동 추가하지 않는다. API JSON과 계약 테스트는 허용 입력으로 지정할 수 있다. 01은 발췌하지 않고 전체를 제공한다.

평가마다 필요한 파일만 모은 폴더 또는 격리된 작업 공간을 사용한다. 폴더와 프롬프트만으로 파일 접근이 강제 차단된다고 가정하지 않는다. 실제 읽은 파일을 기록한다.

## 5. 생성, 평가와 반영

1. Task의 필수 입력과 적용 정책을 확인한다.
2. 문서는 별도 후보 파일에, 코드는 기준 버전과 구분되는 작업 공간에 작성한다.
3. G1을 확인한다. 문서는 승인 양식과 필수 항목, 코드는 빌드와 관련 테스트 및 diff를 검사한다.
4. 같은 대상 버전으로 A와 B를 평가한다.
5. 사용자가 원본 지적을 보존한 결정표를 작성한다.
6. G2로 대상 버전, 원본 행과 결정을 대조한 뒤 수용 항목만 반영한다.
7. R1 반영본을 새 작업에서 R2 평가한다. 내용 변경이 없으면 같은 검증을 기계적으로 반복할 필요는 없다.
8. 최종 후보의 검사와 diff를 확인하고 사용자가 완료를 승인한다.

문서의 3부 구조는 해당 작업이 실제로 채택한 경우에만 적용한다. API 명세는 기능별 요청과 응답 양식을 사용한다. 코드에 문서 형식을 강제하지 않는다.

R2 이후 수정한 내용도 검증해야 한다. 최종 수정의 근거가 없거나 실제 치명이 남으면 미완료다. 오판 정정은 원래 지적을 남기고 근거, 대안, 안티패턴과 사용자 판단으로 기록한다.

## 6. 코드 평가 실행 범위

평가자는 승인된 명령만 지정한 작업 디렉터리에서 실행한다. 소스와 테스트는 수정하지 않는다. 빌드 출력, 로그, 임시 파일과 테스트 DB는 Task가 허용한 범위에서만 변경한다.

환경이 준비되지 않거나 테스트 DB를 특정할 수 없으면 실행하지 못한 항목을 기록한다. 생성자의 통과 주장과 직접 실행한 통과를 구분한다. 미실행을 통과나 지적 0건으로 바꾸지 않는다.

## 7. 완료와 재개

완료에는 Task 충족, G1과 G2 확인, 수용 변경 반영, 승인하지 않은 변경 없음, 최종 버전 검증과 사용자 승인이 필요하다.

| 상황 | 처리 |
|---|---|
| 입력 또는 평가 기준 누락 | 해당 검증과 작업을 미완료로 기록 |
| 문서 형식 실패 | 최초 검사 후 최대 1회 보정, 계속 실패하면 기록 |
| 코드 검사 실패 | 실패 원인과 수정 범위를 기록하고 필요한 검사를 다시 실행 |
| 결정표 행 누락, 변조 또는 빈 결정 | 반영하지 않고 원본과 차이를 보고 |
| 앱 중단 또는 사용량 소진 | 마지막 성공 단계와 산출물을 저장. LLM API로 전환하지 않음 |
| 저장 또는 커밋 실패 | 성공한 생성과 검증을 반복하지 않고 실패한 단계부터 재개 |

진행 기록에는 대상 파일과 버전, 마지막 성공 단계, 미해결 항목, 다음 작업과 실제 사용 시간을 남긴다. Git을 사용하는 작업 공간에서는 사용자 완료 승인 후 해당 Task에 속한 변경만 저장한다.

## 8. 현재 남은 준비

- 사용할 01 버전과 필요한 설계 입력 확정
- 원문 의존 Step에 필요한 07 확보
- 실제 평가 기준의 축, 심각도와 출력 스키마 확정
- 첫 Task의 정책, 파일 범위와 테스트 명령 작성
- 한 기능에서 생성부터 최종 검증까지 전달 흐름 실행

문서 수정은 위 준비나 실제 코드 구현의 완료를 의미하지 않는다.
