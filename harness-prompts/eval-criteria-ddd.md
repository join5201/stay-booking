# 설계 문서 평가 기준 (ddd-blind-review 원본 발췌)

버전: 2026-09-07 v1
출처: Claude Code 스킬 ddd-blind-review의 SKILL.md 원본. 축, 심각도, 출력 스키마, 입력 계약을 그대로 옮겼다. 표현을 바꾸지 않았다.
용도: harness-prompts/evaluate.md의 허용 입력 "실제 평가 기준"에 지정하는 파일. 설계 문서 작업에만 쓴다. 코드 작업의 평가 기준은 별도 파일로 만든다(미작성).
주의: 이 파일이 있다고 해서 Codex 평가가 스킬의 정식 평가와 동등한 것은 아니다. 평가자가 다르고 실행 환경이 다르다. 같은 축과 같은 스키마를 쓴다는 뜻이다.

## 1. 입력 계약

### 넘기는 것

- 검증 대상 문서 경로
- 배경 문서. 원본은 o2o-review-input-pack.md 하나로 고정한다
- 상위 입력 문서 경로 (이벤트 목록, 커맨드와 액터 등)
- 해당 Step의 판정 축과 출력 스키마
- 독자 프로필

### 넘기지 않는 것

- 대화 로그, 세션 요약
- 쟁점에 대한 권고안과 그 근거가 담긴 계획 문서 (예: ddd-plan.md 3장, 4장)
- 어느 부분이 약한지, 어디를 봐달라는 힌트
- 이 문서가 잘 나왔다는 자평

원본 문장: "계획 문서를 통째로 넘기면 안 된다. 배경이 필요하면 쟁점과 권고를 제거한 입력 팩을 쓴다. 입력 팩이 없으면 먼저 만든다. 편의상 통째로 던지는 것이 이 스킬을 무력화하는 유일한 방법이다."

결정 (2026-09-07): 입력 팩만 넣는다. 01 전체는 넣지 않는다. 10-4 v4 1절의 "01 전체 제공" 행은 이 결정으로 갱신한다.

## 2. 두 가지 모드

감사 모드(기본): 문서를 읽고 축에 따라 결함을 찾는다. 모든 Step 산출물에 적용한다.
독립 재도출 모드: 상위 입력과 불변식만 주고 결론을 스스로 도출하게 한 뒤 문서의 결론과 대조한다. 비싸므로 판단이 갈리는 결정 한두 개에만 쓴다. 재도출 프롬프트에는 후보안 2개 이상과 각각의 규칙 충돌을 적게 하고, 결론을 하나로 좁히지 않게 한다. 문서의 결론을 미리 알려주지 않는다.

## 3. Step별 판정 축

문서 종류를 먼저 판별하고 해당 축만 적용한다. 축을 전부 섞어 던지지 않는다.

### 컨텍스트 맵

| 축 | 판정 질문 |
|---|---|
| 언어 충돌 | 같은 단어가 컨텍스트마다 다른 의미인데 용어 사전이 나뉘지 않았나 |
| 소유권 단일성 | 한 데이터를 두 컨텍스트가 변경하나 |
| 의존 순환 | Upstream/Downstream 화살표에 사이클이 있나 |
| 공유 커널 남용 | 공유로 올린 것이 안정성, 보편성, 단순성 3기준을 통과하나 |
| 이벤트 고아 | 상위 문서의 이벤트 중 어느 컨텍스트에도 배정되지 않은 것 |
| 관계 미지정 | 화살표는 있는데 동기/비동기와 관계 패턴이 비어 있는 곳 |

### 애그리거트와 CRC

| 축 | 판정 질문 |
|---|---|
| 불변식 없는 루트 | 지켜야 할 규칙이 없는데 애그리거트로 잡혔나 (그건 엔티티다) |
| 트랜잭션 다중 수정 | 한 커맨드가 애그리거트 2개 이상을 동시에 바꾸나. 예외라면 문서가 예외임을 선언하고 근거를 적었나 |
| 경계 넘는 객체 참조 | ID 타입 VO여야 할 곳에 객체 참조나 @ManyToOne이 있나 |
| 크기 폭발 | 컬렉션이 시간이나 데이터 증가에 비례해 무한히 커지나 |
| 커맨드 고아 | 상위 문서의 커맨드 중 어느 루트의 메서드로도 매핑되지 않은 것 |
| 책임 누수 | 애플리케이션 서비스가 가져야 할 조율 책임이 루트에 들어갔거나 그 반대 |

### DbC 계약

| 축 | 판정 질문 |
|---|---|
| 검증 가능성 | 불변식이 테스트 문장으로 쓰였나. 안전하게 처리한다 같은 서술은 계약이 아니다 |
| 계약 완결성 | 루트 메서드마다 선행조건, 불변식, 후행조건, 위반 예외 네 칸이 다 찼나 |
| 상태전이 폐쇄성 | 금지 전이가 명시됐나. 도달 불가 상태나 빠져나갈 수 없는 상태가 있나 |
| 멱등 계약 | 재호출 무해가 후행조건에 실제로 적혔나 |
| 시간적 불변식 | 확정 후 변하면 안 되는 값이 어느 시점, 어느 필드로 고정되나 |
| 가드 누락 | 횟수나 시간 조건이 걸린 전이에 가드 식이 적혔나 |

### 정책과 Saga

| 축 | 판정 질문 |
|---|---|
| 이벤트 전수 커버리지 | 이벤트 각각에 대해 자동 후속 행동의 유무가 판정됐나 |
| 실패 경로 | 각 정책의 실행 커맨드가 실패했을 때의 대응이 있나 |
| 멱등 전략 | 비동기 정책에 중복 수신 대비가 있나 |
| 표기 일치 | 일관성 유형 표기와 실제 처리 방식이 어긋나지 않나 |
| 경합 조건 | 두 정책이 같은 대상을 동시에 건드릴 수 있나. 어느 쪽이 이기는지 정해졌나 |

### 패키지 구조와 구현 매핑 (Step 9)

| 축 | 판정 질문 |
|---|---|
| 경계 위반 | 금지되어야 할 컨텍스트 간 의존이 규칙으로 막히나 |
| Repository 단위 | 애그리거트 루트가 아닌 것에 Repository가 정의됐나 |
| 계약 하강 | 계약표 항목 중 테스트 케이스로 내려가지 않은 것 |
| 레이어 역전 | domain이 infrastructure를 참조하나 |

### 공통 축 (모든 문서에 항상 적용. 평가자 B 담당)

- 추적성 양방향: 상위 문서 항목이 하위에 전부 반영됐나, 그리고 하위에 근거 없이 새로 등장한 항목이 있나
- 결정 근거의 자립성: 왜 그렇게 정했는지가 문서 안에 있나. 결론만 있고 근거가 없는 곳
- 요구사항 역추적: 시스템 보장 요구사항 각각이 어느 불변식, 어느 정책으로 내려갔는지 문서만 보고 짚을 수 있나

## 4. 출력 스키마

```
## 판정 요약
치명 N / 보통 N / 확인필요 N

## 상세
| 심각도 | 위치 | 위반 축 | 문제 | 문서 내 근거 | 수정 제안 |

## 요구사항 역추적표
| 요구사항 | 문서에서 대응되는 항목 | 커버 여부 |
```

harness-prompts/evaluate.md와 decision-table.md가 요구하는 추가 필드(원본 번호, 지적 ID, 위반 기준, 실제 읽은 파일과 버전, 시작과 종료 시각, 미확인 범위)는 이 스키마 뒤에 보조 표로 붙인다. 원본 스키마의 열은 바꾸지 않는다.

## 5. 심각도 정의

- 치명: 요구사항이나 불변식이 깨진다. 이대로 코드로 내려가면 버그가 된다
- 보통: 문서가 불완전하거나 규칙과 어긋나지만 치명적이지는 않다
- 확인필요: 문서만으로는 판단할 수 없다. 배경을 아는 사람의 확인이 필요하다

확인필요 등급을 반드시 유지한다. 블라인드는 문맥 부족 오판이 반드시 나오는데, 이걸 치명으로 올리면 멀쩡한 결정을 뒤집게 된다. 사용자가 반박할 수 있는 슬롯이 확인필요다.

## 6. 평가자 분할

축이 여섯 개 이상이면 둘로 나눈다. 한 평가자가 다 보면 그 안에서 우선순위가 고정된다.

- 평가자 A: 규칙 준수 (해당 Step 축)
- 평가자 B: 추적성과 자립성 (공통 축 3개)

평가자에게 주는 지시 원문: "너는 이 문서가 만들어진 논의를 보지 못했고 볼 필요도 없다. 문서에 적힌 것만으로 판정한다. 금지: 파일 수정, 문체나 표현 지적, 문서에 없는 내용을 추측으로 채우기. 판단이 안 서면 확인필요로 남긴다."

## 7. 리포트 처리 규칙

1. 두 평가자의 상세 표를 원문 그대로 이어붙여 사용자에게 제시한다
2. 확인필요 항목에 한해 반박할 수 있고, 반박 내용을 따로 표시한다
3. 치명과 보통 항목은 반박하지 않는다. 수용 여부는 사용자가 정한다
4. 사용자가 수용한 항목만 문서에 반영한다
5. 재검증은 최대 1회

## 8. 하지 말 것

- 계획 문서나 쟁점 문서를 통째로 평가자에게 넘기기
- 평가자에게 파일 수정 권한 주기
- 리포트를 요약하면서 자기 결정에 불리한 지적 빼기
- 확인필요 등급을 없애고 이분법으로 판정시키기
- 문서의 결론을 알려준 뒤 재도출 시키기
- 검증 결과를 근거로 사용자 확인 없이 설계 결정 바꾸기
