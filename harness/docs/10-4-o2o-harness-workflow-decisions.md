# O2O 하네스 실행 방식 결정

최초 작성: 2026-09-07
최종 갱신: 2026-09-08 v5 (평가 입력 01 결정 번복: 전체 제공에서 입력 팩으로. 입력 문서명 정정, 평가 기준 파일 행 추가)
성격: 살아 있는 결정 기록이다. harness/docs/의 다른 문서(10-5~10-8)는 이력이라 갱신하지 않지만 이것은 실행 방식의 현재 결정을 담아 갱신한다. 사용자 결정 추가 기록. 기존 계획의 API 직접 호출 방식을 아래 내용으로 변경한다.
입력: harness/project-sync/o2o-review-input-pack.md, 사용자의 실행 방식 결정
적용 범위: 설계 문서 생성과 평가 및 반영, 하네스 실제 적용, O2O 서비스 구현 계획

## 1. 확정

| 항목 | 결정 |
|---|---|
| 비용 조건 | 별도 LLM API 과금을 사용하지 않는다 |
| 생성 | 사용자가 Claude Code 앱에서 실행한다 |
| 평가 | 사용자가 Codex 앱에서 평가 대상 파일을 읽게 하여 실행한다 |
| 결과 전달 | 사용자가 두 앱을 각각 열고 결과 문서를 전달한다 |
| 앱 간 자동 호출 | 이번 범위에 포함하지 않는다 |
| 인증 | 각 앱에서 사용하는 기존 구독 로그인으로 진행한다 |
| 최종 결정 | 사용자가 평가 결과의 수용, 거부, 반박을 결정한다 |
| API 기반 Java 하네스 | 구현을 보류한다 |
| 평가 입력 01 | 입력 팩만 제공한다. 01 전체를 평가자에게 주지 않는다 (2026-09-08 v5에서 번복. 근거는 10-8 1-2) |
| 평가용 예시 | 사용하지 않는다. 08-3을 포함한 기존 감사 문서의 지적을 프롬프트 예시로 넣지 않는다 |
| 치명 지적의 오판 판단 | 사용자가 근거, 대안, 안티패턴을 남기고 판단한다 |
| 업무별 사용 시간 | 지금 고정하지 않고 개발하면서 기록하고 보완한다 |

생성 모델 후보는 Claude Code의 Opus다. 평가 모델 후보는 Codex의 GPT-6 Astra 또는 GPT-5.6 Sol이다. 앱별 구체 모델 선택은 아직 확정하지 않았다.

## 2. 작업 흐름

1. 사용자가 이번 Step의 작업 유형, 입력 버전, 목표, 변경 범위, 채택한 정책과 완료 기준을 정한다.
2. Claude Code에서 문서 초안 또는 격리된 코드 변경을 만들고 필요한 검사를 실행한다.
3. 작업 유형에 맞는 G1 검사 후, 사용자가 입력 팩과 평가 대상 및 허용한 자료를 준비한다. 01 전체는 넣지 않는다. 과거 평가 지적을 예시로 넣지 않는다.
4. Codex의 새 작업에서 해당 자료만 읽게 하여 평가하고 리포트를 저장한다.
5. 사용자가 리포트를 검토하고 결정표를 채운다. 치명 지적을 오판으로 판단하는 경우에는 근거, 대안, 안티패턴을 남긴다.
6. 결정표를 Claude Code에 전달해 수용한 내용을 반영한다.
7. 최종 diff와 필요한 검증 결과를 확인한 뒤 사용자가 완료를 확정한다.

기존의 재평가 최대 1회 원칙은 유지한다. 재평가 횟수 소진을 완료 근거로 사용하지 않는다. 오판 정정은 5절에 따라 기록한다. 마지막 반영본에 필요한 검증이 남아 있으면 미완료로 기록한다.

## 3. 기존 계획에서 바뀌는 부분

| 기존 결정 | 변경 |
|---|---|
| Java SDK로 Messages API 직접 호출 | 이번 실행 방식에서 제외 |
| API 키와 API 모델 문자열 설정 | 이번 실행 방식에서 제외 |
| 스트리밍, SDK 재시도, maxTokens 설정 | 이번 실행 방식에서 제외 |
| Spring 기반 하네스와 fake/live 프로파일 | 구현 보류 |
| 하네스가 문서를 읽어 프롬프트에 인라인 | 사용자가 각 앱에서 필요한 파일을 읽도록 지시 |
| 명령으로 생성, 평가, 반영 자동 연결 | 사용자가 문서를 전달하며 단계별 실행 |
| G1과 G2 | 검사할 내용은 유지. 앱에서 자동 강제된다고 가정하지 않음 |
| 상태 파일과 진행 기록 | 인계 기록으로 유지 가능. 앱이 완료 여부를 임의로 확정하지 않음 |
| API 비용 상한 결정 | 직접 API 호출을 사용하지 않으므로 이번 결정 대상에서 제외 |
| 평가 입력에서 01 차단 | 유지. 입력 팩만 허용 (v5에서 v4의 폐기 결정을 되돌림) |
| 기존 감사 문서의 few-shot 예시 선정 | 폐기. 평가용 예시 미사용 |
| 업무별 권장 시간과 상한 제안 | 확정 기준으로 적용하지 않음. 개발 중 실제 사용 시간을 바탕으로 보완 |
| 평가 기준 파일 미확보 | 해소. 설계는 harness/prompts/eval-criteria-ddd.md, 코드는 harness/prompts/eval-criteria-code.md v0 |
| G1과 G2를 사람이 눈으로 확인 | 해소. harness/tools/check.mjs의 fill, g1, g2가 기계로 검사하고 사람이 서명한다 |

G1과 G2를 자동 검사할 필요가 생기면 LLM API를 호출하지 않는 로컬 검사 도구로 구현할 수 있다. 별도 Spring 프로젝트가 필수인 것은 아니다.

| 검사 | 문서 작업 | 코드 작업 |
|---|---|---|
| G1 | 승인한 양식, 필수 필드, 예시와 내부 링크 확인 | 빌드, 관련 테스트, 코드 검사와 허용 범위 diff 확인 |
| G2 | 원본 지적과 사용자 결정의 행, 내용 및 버전 대조 | 같은 절차에 파일 목록과 코드 버전 대조 추가 |

API 명세는 독립적인 문서로 작성하고 요청, 응답과 오류 중심의 양식을 따른다. 모든 문서에 입력 요약, 본문, 핫스팟의 3부 구조를 강제하지 않는다. 코드에는 문서용 제목이나 강조 규칙을 적용하지 않는다.

## 4. 블라인드 평가의 입력 관리

현재 계획 검토 대화에는 권고, 해결안, 기존 평가 결과의 설명이 들어 있다. 이 대화를 실제 블라인드 평가에 재사용하지 않는다.

- 평가마다 새 Codex 작업을 사용한다.
- 01은 제공하지 않는다. 입력 팩(harness/project-sync/o2o-review-input-pack.md 또는 승인한 v3)만 제공한다. 스킬 원본이 01 전체 제공을 이 스킬을 무력화하는 행위로 지목한다(10-8 1-2).
- 평가 대상과 나머지 허용 입력 자료를 함께 제공한다. 별도 평가 폴더에 필요한 파일만 모으는 방식을 권한다.
- 생성 대화, harness/docs/ 전체, harness/state/ 전체, 이전 평가 리포트는 평가 입력에 포함하지 않는다.
- 08-3을 포함한 기존 감사 문서의 지적이나 별도로 만든 사례를 평가 프롬프트의 예시로 사용하지 않는다.
- 평가 리포트에 실제 읽은 파일과 문서 버전을 남긴다.
- 평가용 폴더와 프롬프트 지시는 입력 혼입을 줄이는 운영 규칙이다. API 요청을 허용 목록으로 조립하던 기존 방식과 같은 강제 차단을 보장하지는 않는다.

평가 성능을 확인하기 위한 검증용 사례와 결과 기록은 프롬프트에 넣는 예시와 구분한다. 예시를 사용하지 않는 결정이 평가 성능 검증까지 생략한다는 뜻은 아니다.

API의 요청과 응답 JSON, 테스트 fixture와 계약 테스트는 평가 대상과 그 검증 자료다. 평가자의 모범 지적이나 과거 감사 해답을 주입하는 예시와 구분해 허용 입력에 명시한다.

코드 평가에서는 승인한 명령을 지정한 테스트 환경에서 실행할 수 있다. 평가자는 소스와 테스트를 고치지 않고, 허용한 빌드 산출물과 로그 및 테스트 DB만 변경할 수 있다. 직접 실행한 결과, 생성자가 전달한 결과와 실행하지 못한 항목을 구분한다.

## 5. 치명 지적의 오판 판단 기록

재평가 후 남은 치명 지적을 사용자가 오판으로 판단하는 경우, 원래 지적을 보존하고 아래 내용을 결정표 또는 연결된 판단 기록에 남긴다.

| 항목 | 남길 내용 |
|---|---|
| 대상 | Step, 평가 라운드, 지적 ID, 평가 대상 문서 버전 |
| 근거 | 오판이라고 판단한 문서 조항, 위치, 반례 등 확인 가능한 근거 |
| 대안 | 검토한 다른 처리 방법과 채택 여부 및 이유 |
| 안티패턴 | 이 문제에서 피해야 할 처리 방식과 그 이유 |
| 결정 | 사용자 판단과 결정 날짜 |

오판으로 정정한 항목은 그 이유를 추적할 수 있게 남긴다. 실제 결함을 인정하면서 감수하는 결정은 오판 정정으로 기록하지 않는다. 최종 완료는 필요한 검증을 마친 반영본에 대해 사용자가 승인한다.

## 6. 업무별 시간 관리

업무별 사용 시간과 최대 실행 시간은 지금 고정하지 않는다. 기존에 제안한 시간표는 확정 기준으로 적용하지 않는다.

입력 정리, 생성, 형식 확인과 전달, 평가, 사용자 판단, 수정 반영, 재평가, 최종 검토에 실제로 쓴 시간을 진행 기록에 남긴다. 시간이 늘어난 이유와 다음 작업에서 보완할 점을 함께 적고, 개발하면서 기준을 정한다.

별도 LLM API 과금을 사용하지 않는 결정은 유지한다. O2O의 로컬 HTTP API 호출과 테스트는 이 제한의 대상이 아니다.

## 7. O2O 서비스 기술 구성

사용자의 현재 구상은 Next.js 프론트엔드, Spring 기반 Java 백엔드, MySQL이다.

이 문서에서 보류하는 Spring 하네스는 개발 보조 프로그램이다. O2O 서비스의 Spring 백엔드 구상을 보류하거나 변경하는 결정이 아니다.

## 8. 실제 적용과 구현 계획으로 범위 확장

사용자는 하네스 기획에 실제 적용과 서비스 구현 계획까지 포함하도록 범위를 확장했다. 초기 세팅, 백엔드 개발과 테스트 코드, 프론트 개발, 연결 테스트, 검증을 필수 항목으로 한다.

이번 구현 계획은 로컬 환경의 개발과 최종 검증까지로 한다. 배포와 운영 준비는 사용자 요청에 따라 제외한다.

세부 작업과 추가 제안은 10-6-o2o-harness-implementation-plan.md에 정리한다. 추가 제안은 해당 문서에서 기울임으로 구분한다. 기존 실행 방식 결정은 유지하며, 작업 목록 작성만으로 실제 적용이나 구현이 완료됐다고 판단하지 않는다.

API 명세 v2의 P01~P11은 제안 상태다. 작업 계약에 적용 정책과 판단을 적기 전에는 확정 전제로 사용하지 않는다. 회원 기능을 제외하는 범위는 유지하며, 양식 예제에 있던 AccessToken과 RefreshToken을 도입한 것으로 해석하지 않는다.
