# 세션별 worktree 분리

최초 작성: 2026-09-09
최종 갱신: 2026-09-10 (6-1절 신설. union이 서버 병합에 안 걸린다)

왜 이 문서가 필요한가: 세 세션이 작업 트리 하나를 공유하는 동안 2026-09-09 하루에만 여섯 번 막혔다. 남의 미커밋 작업이 커밋에 쓸려 들어갔고, 브랜치를 못 바꿔 백업하고 되돌리기를 네 번 했다. 이 문서가 그 분리의 근거와 절차와 남는 제약을 적는다.

## 1. 무엇이 문제였나

작업 트리가 하나면 체크아웃된 브랜치도 하나다. 세션이 셋이면 셋이 그 하나를 두고 다툰다.

| 사고 | 언제 |
|---|---|
| 개발 세션이 경로를 안 적고 커밋해 문서 세션의 미커밋 작업이 쓸려 들어갔다 | 2026-09-08 PR 33 |
| 브랜치를 못 바꿔 작업을 트리에 올려 둔 채 대기 | 2026-09-09 네 번 |
| 병합된 산출물이 작업 트리에 없어 다음 단계가 막힘 | 2026-09-09 세 번 |

## 2. 왜 그동안 못 나눴나

계약의 경로 칸이 절대경로였다. 다른 폴더의 worktree에서 검사기를 돌려도 그 절대경로가 원래 폴더를 가리켜 남의 파일을 해시했다. 실패가 아니라 조용한 오답이라 더 나빴다.

이슈 26이 그것을 고쳤다. 검사기가 상대경로를 저장소 루트 기준으로 풀고, 루트는 스크립트 위치에서 유도한다. 그래서 트리마다 자기 파일을 본다.

2026-09-09 실측이다.

| 트리 | 검사기가 유도한 루트 |
|---|---|
| C:/Dev/potenup/99_projects/o2o | C:\Dev\potenup\99_projects\o2o |
| C:/Dev/potenup/99_projects/o2o-dev | C:\Dev\potenup\99_projects\o2o-dev |

## 3. 배치

| 트리 | 경로 | 누가 쓰나 |
|---|---|---|
| 본 트리 | C:/Dev/potenup/99_projects/o2o | 문서와 하네스 세션 |
| 개발 트리 | C:/Dev/potenup/99_projects/o2o-dev | 개발 세션 |

저장소 밖 형제 폴더로 둔 이유 둘이다. 상위 C:/Dev/potenup 저장소가 .gitignore의 /99_projects/ 규칙으로 이 폴더들을 안 본다. 그리고 저장소 안에 두면 .gitignore를 고쳐야 하고 검사기의 루트 유도가 자기 안의 트리를 만나 헷갈린다.

## 4. 만드는 절차

본 트리에서 한 줄이다.

    git worktree add ../o2o-dev <브랜치>

한 브랜치는 한 트리에만 체크아웃된다. 이미 다른 트리가 잡은 브랜치는 거부된다. 그것이 이 방식의 안전장치다.

## 5. 따라오지 않는 것

추적 제외 파일은 새 트리에 안 생긴다. 사람이 옮긴다.

| 파일 | 무엇 | 어떻게 |
|---|---|---|
| backend/.env | MySQL 접속값 | 본 트리에서 복사한다. deny 규칙이 모델의 접근을 막으므로 사람이 한다 |
| .claude/settings.local.json | 답변 형식 Stop 훅 | 필요하면 복사한다. 10-9 7절이 로컬 전용으로 결정했다 |
| backend/build, backend/.gradle | 빌드 산출물 | 새 트리에서 다시 빌드한다 |

env.example은 추적되므로 따라온다.

## 6. 남는 제약 (2026-09-10 기록 파일 행 갱신)

| 제약 | 내용 |
|---|---|
| 기록 파일은 여전히 공유 | progress.md와 troubleshooting.md와 knowledge.md는 같은 파일이다. merge=union이 로컬 병합에서만 충돌을 막는다. 6-1절. 순서는 어느 쪽이든 보장되지 않는다 |
| 병합은 각 트리가 따로 | 한쪽에서 main이 갱신돼도 다른 트리는 자동으로 안 받는다. git merge origin/main을 각자 돌린다 |
| CLAUDE.md 1절의 루트 표기 | 본 트리 경로 하나만 적혀 있다. 트리가 둘이 된 사실은 이 문서가 정본이다 |
| 옛 브랜치의 절대경로 | 이슈 26 이전 브랜치는 계약에 절대경로가 남아 있다. main을 병합해야 상대경로 판이 온다 |

마지막 것이 개발 트리를 만든 직후 실제로 났다. feat/task-s9-catalog-skeleton이 PR 41 이전이라 계약에 절대경로 34곳이 남아 있었고 fill이 자기 해시 검사에서 걸렸다.

### 6-1. union이 걸리는 자리와 안 걸리는 자리 (2026-09-10 신설)

merge=union은 같은 자리에 들어온 양쪽 줄을 둘 다 남기는 병합 방식이다. 충돌 표시를 내지 않는다. 기록 파일 셋이 이것으로 여러 세션의 추가를 받는다.

문제는 이 설정을 누가 읽느냐다. 병합 방식을 고르는 것은 병합을 실행하는 쪽이고, 그 선택은 .gitattributes에서 온다.

| 누가 병합하나 | union이 걸리나 |
|---|---|
| 로컬 git merge | 걸린다 |
| 로컬 git merge-tree | 걸린다 |
| GitHub의 PR 병합 가능 여부 계산 | 안 걸린다 |

2026-09-10 재현이다. PR 61과 62가 각각 main에서 갈라져 progress.md에 행을 더했다. 61을 병합하자 62가 CONFLICTING으로 바뀌었다. 같은 두 커밋을 로컬에서 병합하면 깨끗이 붙는다. 같은 날 열려 있던 PR 77로 한 번 더 확인했다. GitHub는 CONFLICTING이라 적는데 로컬 git merge-tree는 충돌 0으로 트리를 만든다. 그 progress.md 셋을 꺼내 재 보면 기본 병합은 충돌 1건, union 병합은 0건이다. union이 그 차이를 만드는 것이 맞다.

그래서 PR을 올리기 전에 브랜치에서 origin/main을 병합한다. 그 병합은 로컬 git이 하므로 union이 걸리고, GitHub는 이미 합쳐진 결과를 받는다. CLAUDE.md 4-1의 5단계다.

이 절을 쓰는 동안 같은 일이 한 번 더 났다. 열려 있던 PR 92가 다른 세션의 병합 뒤 CONFLICTING으로 바뀌었고, 그 브랜치에서 origin/main을 병합해 밀어 넣자 MERGEABLE로 돌아왔다. 절차가 실제로 푼다는 확인이다.

union에 흠이 하나 더 있다. 양쪽에 똑같이 있는 줄을 두 자리에 나눠 넣으면 그 줄이 두 번 남는다. 2026-09-10에 85 커밋만큼 벌어진 브랜치를 합치다가 행 넷이 두 번 들어갔다. 같은 행이 두 자리에 있으면 그 Task의 마지막 행을 읽는 재개 판정이 흔들린다. 벌어짐이 클수록 잘 난다. 5단계를 매번 밟으면 벌어짐이 작게 유지되어 이 흠도 같이 줄어든다.

## 7. 세션이 지켜야 할 것 (2026-09-10 한 행 추가)

| 규칙 | 왜 |
|---|---|
| 자기 트리에서만 작업한다 | 남의 트리에 파일을 만들면 그 세션이 자기 것으로 착각한다 |
| 남의 트리를 지우지 않는다 | 8절. 병합됐다는 것과 그 세션이 끝났다는 것은 다른 말이다 |
| 커밋할 때 경로를 명시한다 | CLAUDE.md 4-1. 트리를 나눠도 기록 파일은 공유라 여전히 필요하다 |
| 브랜치를 바꾸기 전에 git status를 본다 | 같은 트리 안에서는 여전히 하나만 체크아웃된다 |
| worktree 목록을 먼저 본다 | git worktree list. 어느 브랜치가 어디 잡혀 있는지가 거기 있다 |
| 자기가 연 임시 트리는 자기가 닫는다 | 8절. 여는 절차만 있고 닫는 절차가 없어서 넷이 쌓였다 |

## 8. 닫는 절차 (2026-09-10 신설)

왜 이 절이 필요한가: 4절에 여는 절차만 있었다. 2026-09-10에 worktree 목록이 여섯이었고 그중 넷이 이미 병합된 브랜치를 잡고 있었다. 병합된 브랜치를 트리가 잡고 있으면 다른 트리에서 그 브랜치를 체크아웃할 수 없고, 목록이 길어져 살아 있는 세션의 자리가 안 보인다.

닫는 것은 그 트리를 연 세션이 한다. 임시 트리는 PR이 병합되는 자리에서 같이 닫는다. 본 트리와 개발 트리 둘은 3절이 고정한 자리라 이 절의 대상이 아니다.

| 순서 | 하는 일 |
|---|---|
| 1 | PR이 병합된 것을 확인한다 |
| 2 | 그 트리에서 git status로 미커밋 0을 확인한다 |
| 3 | 다른 트리에서 git worktree remove <경로> |
| 4 | git branch -d <브랜치>. 원격에도 있으면 git push origin --delete <브랜치> |
| 5 | harness/state/progress.md에 한 행 |

3단계를 다른 트리에서 하는 이유는 git이 자기 자신을 지우지 못하기 때문이다. 본 트리에서 하면 된다.

git worktree remove가 미커밋 파일 때문에 거부하면 그 거부가 안전장치다. force를 쓰기 전에 그 파일이 무엇인지 본다.

| 그 파일이 | 어떻게 |
|---|---|
| 이미 커밋된 것의 사본이면 | tmp/_moved/로 옮기고 force로 지운다(CLAUDE.md N2) |
| 그렇지 않으면 | 지우지 않는다. 그 세션이 처리할 때까지 둔다 |

### 8-1. 남의 트리를 지우지 않는다

2026-09-10에 한 세션이 병합된 브랜치를 잡은 트리 넷을 지웠다. 넷 다 미커밋 0이었고 넷 다 main에 들어가 있었다. 그런데 그중 하나는 세션이 살아 있었고, 지운 직후 같은 브랜치로 트리를 다시 만들어 작업을 이어갔다. 그 세션은 검사기를 고치는 중이었다.

브랜치가 병합됐다는 것은 그 PR이 끝났다는 뜻이지 그 세션이 끝났다는 뜻이 아니다. 세션은 병합 뒤에도 같은 브랜치에서 다음 작업을 이어갈 수 있다.

| 무엇으로 판정하나 | 근거로 쓸 수 있나 |
|---|---|
| 브랜치가 main에 병합됐다 | 안 된다. 세션이 이어서 쓸 수 있다 |
| 미커밋이 0이다 | 안 된다. 방금 커밋하고 다음 편집을 시작하는 중일 수 있다 |
| 그 세션이 자기 트리를 닫았다 | 된다. 이것만 근거다 |

밖에서는 세션이 살아 있는지 알 수 없다. 그래서 정리는 각 세션의 마지막 단계이지 다른 세션의 청소 작업이 아니다. 목록에 오래된 트리가 보이면 지우지 말고 사람에게 알린다.

이 판은 세션별 worktree 분리의 기록이다. 승인 전에는 확정본으로 인용하지 않는다.
