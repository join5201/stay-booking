# 하네스 결함 넷 수정 계획 (10-12)

최초 작성: 2026-09-09
최종 갱신: 2026-09-09 (10-10에서 10-12로. 10-10과 10-11이 각각 다른 세션의 문서와 겹쳤다. 번호를 먼저 잡는 절차가 없어서 나는 충돌이다)

왜 이 파일이 필요한가: task-S9-catalog 한 바퀴가 끝나면서 동결이 풀렸고 관찰 15건 중 실제로 고쳐야 하는 넷이 남았다. 넷을 한꺼번에 손대면 어느 변경이 무엇을 깼는지 가릴 수 없다. 이 파일이 순서와 경계를 정한다.

근거: harness/out/task-S9-catalog-R1/step9-verification.md 3-4절, harness/state/troubleshooting.md 2026-09-08과 09 행.

| D | 계약의 절대경로가 세션 분리를 막는다 | 26 | 양식과 검사기와 계약 셋 |

D가 이 계획과 무관하게 다른 세션에서 끝났다. 3-4절의 D1부터 D4는 그대로 두되 이미 이뤄진 것으로 읽는다. 여기서 얻은 것은 계획을 쓴 세션과 실행할 세션이 다르면 계획이 곧 낡는다는 것이다. 이 넷은 원래 하네스 세션의 몫이고 개발 세션이 손댈 일이 아니었다. dev-ptcf-prompt.v3.md 3절 선택 규칙의 마지막 줄이 그것을 이미 금지하고 있었다.

## 2. 순서와 근거

A, B, C, D 순으로 간다.

| 순서 | 왜 이 자리인가 |
|---|---|
| A 먼저 | 되돌리기 쉽다. 설정 한 줄이고 잘못되면 그 줄만 되돌린다. 검사기와 문서를 안 건드린다 |
| B 다음 | 문서만 고친다. 코드도 검사기도 안 건드린다 |
| C 다음 | 표 하나를 다시 매긴다. 진행 기록을 읽는 규칙에 영향이 있어 A와 B보다 뒤다 |
| D 마지막 | 가장 크다. 양식과 검사기와 계약 셋을 한꺼번에 건드리고 검사기 테스트가 따라온다 |

작은 것부터 가는 이유가 하나 더 있다. A와 B와 C가 각각 커밋 하나로 끝나면 D를 하다 막혔을 때 그 셋은 이미 병합돼 있다. 큰 것을 먼저 하면 셋이 뒤에 묶여 같이 멈춘다.

## 3. 각 항목의 경계

### 3-1. A. deny의 .env 규칙 (이슈 39)

| 항목 | 내용 |
|---|---|
| 고칠 파일 | .claude/settings.json, harness/docs/10-15 3절의 deny 이유 표 (2026-09-10 CLAUDE.md 4-1에서 옮김) |
| 무엇을 | Edit(**/.env.*)의 범위에서 .env.example과 .env.sample을 뺀다 |
| 확인 | 좁힌 뒤 .env와 .env.local이 여전히 막히는지 손으로 시험한다. 통과 케이스와 차단 케이스를 짝으로 |
| 하지 않을 것 | Read 쪽 deny는 건드리지 않는다. 읽기는 값이 프롬프트로 들어오는 경로라 성격이 다르다 |

### 3-2. B. 평가 기준의 요구사항 개수 (이슈 38)

| 항목 | 내용 |
|---|---|
| 고칠 파일 | harness/prompts/eval-criteria-code.md 3절 |
| 무엇을 | R1부터 R6을 R1부터 R5로. 정본이 입력 팩 2절임을 명시. 대상 묶음과 무관한 요구사항은 해당 없음으로 적고 미커버로 적지 않는다는 한 줄 추가 |
| 확인 | 입력 팩 2절과 개수가 같은지 눈으로 대조 |
| 하지 않을 것 | 평가 축 자체는 건드리지 않는다. 이 이슈는 개수와 표기다 |

### 3-3. C. 프롬프트의 단계 번호 (이슈 37)

| 항목 | 내용 |
|---|---|
| 고칠 파일 | harness/prompts/dev-ptcf-prompt.v3.md 3절 표와 199행 |
| 무엇을 | 표 번호를 계약 8절에 맞춘다. 계약 개정은 단계 0이 아니라 별도 행으로 두거나 표 밖으로 뺀다 |
| 확인 | 계약 8절과 나란히 놓고 같은 번호가 같은 일을 가리키는지 대조 |
| 하지 않을 것 | 계약 8절의 번호는 안 바꾼다. 진행 기록이 그 번호로 쌓여 있다 |

### 3-4. D. 계약의 절대경로 (이슈 26)

가장 크다. 넷으로 쪼개 커밋한다.

| 순서 | 무엇 | 되돌리면 |
|---|---|---|
| D1 | check.mjs fill이 상대경로를 ROOT 기준으로 풀어 해시한다. 절대경로도 당분간 받고 경고한다. 테스트를 통과와 경고 케이스로 짝지어 붙인다 | 검사기가 절대경로만 받던 상태로 |
| D2 | harness/prompts/task-contract.md 양식의 절대경로 칸을 상대경로로 | 양식만 |
| D3 | 기존 계약 셋을 상대경로로. task-S2.md 28곳, task-S8.md 22곳, task-S9-catalog.md 약 20곳 | 계약만. D1이 절대경로를 아직 받으므로 안전하다 |
| D4 | evaluate-A.md와 evaluate-B.md 양식의 같은 칸 | 평가 요청 양식만 |

D1이 먼저인 이유는 뒤의 셋이 D1 없이는 fill을 통과하지 못하기 때문이다. 절대경로를 당분간 계속 받게 두는 이유는 D3이 끝나기 전에 다른 세션이 옛 계약으로 fill을 돌려도 죽지 않게 하기 위해서다.

절대경로 지원을 언제 뺄지는 이 계획에서 정하지 않는다. D4까지 끝나고 한 바퀴 돌려 본 뒤 별도로 정한다.
