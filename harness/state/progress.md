# 진행 기록 (harness/state/progress.md)

최초 작성: 2026-09-07
최종 갱신: 2026-09-11 (표 중간에 있던 재작성 주석을 표 앞으로 옮김. 그 주석 뒤에 더한 행 130개가 머리글과 떨어져 표로 렌더링되지 않았다. 행은 고치지 않았다)

왜 이 파일이 필요한가: 재개할 때 어디까지 성공했는지 모르면 이미 성공한 생성과 검증을 다시 돌린다(HR6). 이 파일이 그 반복을 막는다. 매 턴 단계 판정의 근거도 이 파일의 마지막 행이다.

## 행 형식 (2026-09-08 H5 확정. 2026-09-10 세 칸 신설)

열두 칸이다. 2026-09-10 이전 행은 아홉 칸이고 뒤의 세 칸이 없다. 그 이유는 이 절 끝에 있다.

| 칸 | 무엇을 적는가 |
|---|---|
| 날짜시각 | YYYY-MM-DD HH:MM |
| Task | 준비 단계는 H0~H6, 실행 단계는 task-S{Step} |
| 라운드 | R1 또는 R2. 준비 단계는 해당 없음 |
| 단계 | 실행 단계는 계약, 생성, G1, 평가A, 평가B, 결정, G2, 반영, 최종 아홉 중 하나. 준비 단계는 준비 |
| 결과 | 아래 status 값 여섯 중 하나와 한 줄 요약 |
| 실패 원인 | 실패했을 때만. 없으면 없음 |
| 교훈 | 다음에 달리 할 것. 없으면 없음 |
| 다음 작업 | 다음 행이 무엇이어야 하는가 |
| 실제 시간 | 실측값 또는 미측정 |
| 증거 | 결과 칸의 주장을 무엇이 받치는가. 돌린 명령과 그 출력, 또는 파일 경로. 없으면 없음 |
| 안 해 본 것 | 떠올렸으나 안 해 본 방법. 다음 세션이 그것부터 본다. 없으면 없음 |
| 대체 | 이 행이 바로잡는 앞 행의 날짜시각. 없으면 없음 |

실패 원인 칸이 재요청과 재평가 프롬프트에 넣는 실패 사유의 원천이다(HR3). 교훈 칸에 같은 항목이 두 번 나오면 07 v3의 DO NOT 블록에 한 줄 올린다(10-8 5-7).

세 칸을 왜 더했나 (2026-09-10). 대조 다섯 중 ECC 대조에서 나왔다(10-14 9-3절 E2, E3, E4).

| 칸 | 무엇을 막나 |
|---|---|
| 증거 | 결과 칸에 applied나 done을 적는 것과 그것이 실제로 됐다는 것은 다르다. 증거 칸이 비면 그 행은 주장이지 기록이 아니다. 결과 파일이 있다는 것을 통과로 읽는 고장이 CLAUDE.md 5-1절에 두 번 적혀 있다 |
| 안 해 본 것 | 실패 원인은 해 보고 안 된 것만 적는다. 떠올렸다가 안 해 본 것은 어디에도 안 남아서 다음 세션이 같은 것을 다시 떠올린다 |
| 대체 | 추가 전용이라 틀린 것으로 밝혀진 행을 고칠 수 없다. 고치는 대신 새 행이 앞 행을 가리킨다. 재개 브리핑이 대체된 행을 셈에서 뺀다 |

기존 행을 왜 안 고쳤나. 2026-09-08 H5 때는 열한 행이라 다시 썼다. 지금은 아흔 행이 넘고 무엇보다 이 파일에 merge=union이 걸려 있다. 전부 다시 쓰는 커밋과 다른 세션의 행 추가가 만나면 union은 충돌을 내지 않고 양쪽을 다 남긴다. 아흔 행이 두 벌이 된다. 그래서 머리글만 열두 칸으로 바꾸고 옛 행은 아홉 칸 그대로 둔다. 읽는 쪽이 두 형태를 다 받는다(harness/tools/check.mjs의 stateRows).

옛 행의 뒤 세 칸은 빈 것이 아니라 없는 것이다. 그때 그 값을 적지 않았다는 사실 자체가 기록이라 나중에 채워 넣지 않는다.

## status 값 여섯

| 값 | 뜻 |
|---|---|
| pending | 시작하지 않았다 |
| drafted | 산출물을 만들었고 사용자 승인을 기다린다 |
| reviewed | 평가 리포트를 받았다 |
| applied | 결정표의 수용 항목을 반영했다 |
| done | 사용자가 최종 승인했다 |
| halted | 막혀서 멈췄다. 실패 원인 칸이 반드시 찬다 |

done은 사용자 최종 승인 행에서만 쓴다. 스크립트도 모델도 쓰지 않는다(HR5).

## 규칙 넷

1. 추가 전용이다. 기존 행을 고치지 않는다. 상태가 바뀌면 새 행을 추가한다. 앞 행이 틀렸으면 새 행의 대체 칸에 그 행의 날짜시각을 적는다.
2. 실행 단계는 각 행의 시작과 끝에 한 행씩 추가한다. 준비 단계는 끝에 한 행이다.
3. 이 파일에는 단계의 진행만 적는다. 막힌 것과 원인은 harness/state/troubleshooting.md, 재사용되는 지식은 harness/state/knowledge.md, 확정된 결정은 harness/decisions/다.
4. 파일 수정 이력은 두지 않는다(2026-09-07 사용자 결정). 2026-09-08 저장소 편입 이후로는 git 로그가 그 역할을 한다.
