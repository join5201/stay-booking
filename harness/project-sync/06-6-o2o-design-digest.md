# O2O 설계 핵심 요약 (애그리거트, CRC, DbC)

작성: 2026-09-04. 이 프로젝트를 처음 보는 사람을 위한 압축본이다.
원본: 06-2(애그리거트와 CRC), 06-4(DbC 계약과 정책). 근거가 궁금하면 각 원본의 explained 문서를 본다.

## 1. 무엇을 만드는가

숙소 예약 서비스다. 호스트가 숙소와 날짜별 재고, 요금을 올리고, 이용자가 예약하고 결제하며, 운영자가 자동 적용 할인(프로모션)을 만든다. 시스템이 반드시 지켜야 할 보장은 다섯이다. 연박은 전부 선점되거나 전무여야 하고(R1), 동시 요청에도 초과 예약이 없어야 하고(R2), 같은 요청이 반복돼도 예약은 하나여야 하고(R3), 선점 상태로 끝난 예약의 재고는 반드시 돌아와야 하고(R4), 확정된 예약의 금액은 이후 요금이나 할인이 바뀌어도 변하지 않아야 한다(R5).

## 2. 경계: 컨텍스트 5개

쉽게 말하면: 부서를 다섯으로 나눴다. 각 부서는 자기 데이터만 고치고, 남의 데이터는 읽거나 요청만 한다.

| 컨텍스트 | 하는 일 |
|---|---|
| 카탈로그 | 판매 대상 정의 (숙소, 객실 타입) |
| 재고와 요금 | 날짜별 수량과 단가. 수량을 바꿀 수 있는 유일한 곳 |
| 프로모션 | 자동 적용 할인 규칙 |
| 예약 | 생성, 확정, 취소, 만료. 전체 흐름의 허브 |
| 결제 | PG 요청과 결과 기록. 예약이 누군지 모른다 (예약이 총액을 실어 보낸다) |

검색은 컨텍스트가 아니라 읽기 전용 화면(읽기 모델)이다.

## 3. 애그리거트 7개

쉽게 말하면: 규칙을 지키는 최소 단위다. 저장과 잠금도 이 단위로 한다.

| 루트 | 컨텍스트 | 핵심 책임 |
|---|---|---|
| Property | 카탈로그 | 숙소 정보 |
| RoomType | 카탈로그 | 객실 타입과 최대 인원 (0보다 큼) |
| DailyInventory | 재고와 요금 | 한 객실 타입의 하루 재고. 총량 >= 판매 + 선점을 항상 지킨다 |
| DailyRate | 재고와 요금 | 한 객실 타입의 하루 단가 (0보다 큼) |
| Promotion | 프로모션 | 조건(지역, 최소 숙박일, 캠페인 기간)과 할인율. 종료하면 다시 못 연다 |
| Booking | 예약 | 기간, 인원, 금액 스냅샷, 상태. 스냅샷은 생성 시 동결 |
| Payment | 결제 | 예약당 하나. 결제 시도 목록을 품고 시도 3회 상한, 승인 유일을 지킨다 |

주의할 결정 둘. 재고는 기간이 아니라 날짜 하나가 한 행이다 (연박은 여러 행을 함께 다룬다). Payment의 상태는 저장하지 않고 시도 목록에서 계산한다.

## 4. 예약의 생애

쉽게 말하면: 예약은 자리 잡기(HELD)로 태어나 결제가 승인되면 확정(CONFIRMED)되고, 시간이 다 되거나 결제가 3회 실패하면 만료(EXPIRED)되며, 확정 후에는 취소(CANCELED)만 가능하다. 이 셋 밖의 이동은 전부 금지다.

허용 전이: HELD에서 CONFIRMED로, HELD에서 EXPIRED로, CONFIRMED에서 CANCELED로. 특히 CONFIRMED에서 EXPIRED로는 절대 못 간다 (확정 예약의 재고가 새는 과거 결함 유형을 막는 금지선).

세 경로가 각각 한 트랜잭션이다.

| 경로 | 한 트랜잭션 안에서 |
|---|---|
| 생성 | 날짜별 재고 N행 선점 + Booking 생성(스냅샷 동결) |
| 확정 | Booking 잠금 + 확정 + 선점을 판매로 이동 ×N |
| 만료와 취소 | Booking 잠금 + 전이 + 재고 반환 ×N |

동시성은 비관적 락으로 푼다. 재고 여러 행은 날짜 오름차순으로 잠그고(교착 방지), Booking과 Payment는 잠근 뒤에 상태를 검사한다.

## 5. 돈의 규칙

쉽게 말하면: 예약이 생기는 순간의 가격표를 사진 찍어 두고(스냅샷), 그 뒤 요금이나 할인이 바뀌어도 사진은 안 바뀐다.

스냅샷에는 날짜별 단가와 할인 배분액, 적용 프로모션의 식별자와 이름, 총액이 들어간다. 할인 총액은 날짜별 단가에 비례해 나누고, 나누어떨어지지 않는 단수는 마지막 날짜에 몰아준다. 배분의 합은 할인 총액과 정확히 같아야 하고, 총액은 날짜별 (단가 - 할인)의 합과 같아야 한다. 결제는 이 총액과 청구액이 다르면 거부한다.

## 6. 자동 반응 (정책 8개)

쉽게 말하면: 사람이 누르지 않아도 시스템이 알아서 하는 일들이다.

| 언제 | 무엇을 |
|---|---|
| 결제가 승인되면 | 예약을 확정한다 (예약이 HELD일 때) |
| 승인이 너무 늦게 왔으면 (이미 만료) | 자동 환불한다 |
| 예약이 확정되면 | 같은 트랜잭션에서 선점을 판매로 바꾼다 |
| 결제가 3회째 실패하면 | 예약을 만료시킨다 |
| 예약이 만료되면 | 같은 트랜잭션에서 선점 재고를 돌려놓는다 |
| 예약이 취소되면 | 환불하고, 같은 트랜잭션에서 판매분 재고를 돌려놓는다 |
| 시간이 지나면 (스케줄러) | 기한 지난 HELD를 만료시킨다 |

재고로 가는 셋은 원칙상 비동기여야 하지만 단일 모듈의 이점으로 같은 트랜잭션에 묶었다(문서에 이탈로 선언됨). 결제와 예약 사이만 진짜 비동기다. 중복 방어는 두 겹이다. PG가 같은 거래번호로 두 번 통보하면 무시하고(1차), 그래도 같은 요청이 두 번 오면 이미 그 상태라고 성공으로 답하며 아무것도 다시 하지 않는다(2차, 재호출 무해).

## 7. 책임 분담 (CRC 요약)

쉽게 말하면: 규칙은 애그리거트가, 흐름은 서비스가 맡는다.

| 역할 | 담당 | 예 |
|---|---|---|
| 자기 규칙 지키기 | 애그리거트 루트 | DailyInventory가 수량 불변식 검사, Booking이 전이 검사 |
| 여러 행의 원자성 | 도메인 서비스 | InventoryAllocationService가 연박 N행을 순서대로 잠그고 전부 아니면 전무 |
| 가격 계산 | 도메인 서비스 | PricingService가 단가와 프로모션을 읽어 스냅샷 재료를 만든다 (검증은 Booking이) |
| 트랜잭션 경계와 컨텍스트 넘는 확인 | 앱 서비스 | BookingApplicationService가 인원 검증, 재고와 결제 호출, 커밋 후 이벤트 발행 |
| 유일성 | DB | 멱등키, 날짜행, 예약당 결제 하나가 전부 유니크 제약 |

## 8. 계약(DbC)이라는 약속

쉽게 말하면: 커맨드마다 부르는 쪽이 지킬 것(선행조건), 실행한 쪽이 보장할 것(후행조건), 언제나 참일 것(불변식)을 표로 못박았다. 어기면 그 자리에서 예외를 던져 누구 잘못인지 바로 드러난다.

대표 예 하나. 예약 확정(confirm)의 계약: 잠근 뒤 상태가 HELD여야 받는다. 이미 CONFIRMED면 아무것도 안 하고 성공으로 답한다(재고 이동과 이벤트도 생략). EXPIRED면 거부한다(늦게 온 승인의 뒤처리는 자동 환불 정책의 몫). CANCELED면 예외다. 실행하면 같은 트랜잭션에서 선점이 판매로 이동하고, 커밋 후에 확정 이벤트가 나간다.

불변식 전체 목록(내부 16, 연관 6, 유일성 4)과 커맨드 22개 전체의 계약표, 상태전이표는 06-4에 있다. 불변식의 문장이 그대로 테스트 이름이 되도록 썼다.

## 9. 아직 안 정한 것

결제 시도가 응답 없이 갇혔을 때의 시간 상한, 승인 유실 창(승인이 확정과 환불 어느 쪽에도 안 잡히는 드문 경합)의 해소 방식은 Step 8에서 정한다. ttl 값 같은 설정 숫자와 패키지 구조, 테스트 변환은 Step 9다.
