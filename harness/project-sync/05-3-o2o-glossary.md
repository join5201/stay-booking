# O2O 컨텍스트별 용어 사전 (Step 4-3)

최초 작성: 2026-09-01 (05-o2o-glossary.md 1, 3~8절로 작성)
최종 갱신: 2026-09-04 v10 (Step 7 확정 반영: 할인 배분 단수 규칙, 캠페인 기간 판정 시점 확정, 결제 상태에 REFUNDED 전이 명시)
자매 문서: 05-1-o2o-ubiquitous-language.md (용어 충돌), 05-2-o2o-bounded-contexts.md (경계와 배분)
자료: 05 경계를 통해 모델을 보호하는 방법

문서 규칙: 새로 추가되거나 내용이 바뀐 절에는 제목 옆에 반영 날짜를 표기한다.
이 문서는 정의 확정본이다. 유비쿼터스 언어는 여기서 끝나는 작업이 아니라 전 단계에 걸친 활동이므로, 이후 단계에서 새 용어가 생기면 이 문서에 반영한다.

## 1. 액터 (2026-09-02 v8: 게스트 → 이용자)

| 한국어 | 영문 | 정의 |
|---|---|---|
| 이용자 | User | 숙소를 예약하고 결제하는 사람. 호스트와 운영자도 넓게는 사용자지만 이 프로젝트에서 이용자는 예약하는 쪽만 가리킨다. v1에서는 userId로만 식별하고 회원 정보는 다루지 않는다 |
| 호스트 | Host | 숙소를 등록하고 재고와 요금을 관리하는 사람 |
| 운영자 | Operator | 플랫폼 측에서 프로모션을 만드는 사람 |
| 외부 PG | Payment Gateway | 결제를 실제로 처리하는 외부 시스템. 우리에게 결과를 통보한다 |

개명 이력: 게스트(Guest)에서 v8에 변경. 03, 04 등 상류 문서와 보드의 게스트 표기는 그 시점 기록으로 남아 있다.

## 2. 숙소 카탈로그 용어 (2026-09-02 v8: 등록과 수정 정의 명확화)

| 한국어 | 영문 | 정의 |
|---|---|---|
| 숙소 | Property | 판매 대상이 되는 건물 또는 시설 단위. 하나의 주소와 지역을 가진다 |
| 객실 타입 | RoomType | 숙소가 판매하는 객실의 종류 |
| 호실 | Room | 실제 배정되는 개별 방. v1 범위 밖이라 쓰지 않는다 |
| 최대 인원 | maxOccupancy | 객실 타입 하나에 묵을 수 있는 최대 인원. 예약의 인원 검증에 쓰인다. 0보다 크다. 하향 수정은 허용되며 기존 확정 예약에 영향을 주지 않는다 (v10: Step 7 확정) |
| 등록 | Register | 판매 대상(숙소, 객실 타입)을 카탈로그에 새로 올리는 것. 새 식별자가 발급되며 같은 대상을 두 번 등록할 수 없다. 수량이나 금액을 만드는 개설(Open), 등록(RegisterRate)과는 대상이 다르다 |
| 수정 | Update | 이미 등록된 대상의 서술적 속성(이름, 설명, 사진, maxOccupancy)을 고치는 것. 식별자는 바뀌지 않는다. 수량과 금액을 고치는 조정(Adjust)과 구분된다 |

## 3. 재고와 요금 용어 (2026-09-04 v9: 반환 원천 추가)

| 한국어 | 영문 | 정의 |
|---|---|---|
| 재고 | Inventory | 특정 객실 타입의 특정 날짜에 저장된 판매 가능 수량 |
| 가용성 | Availability | totalCount에서 soldCount와 heldCount를 뺀 계산 결과. 저장하지 않는다 |
| 총 수량 | totalCount | 그날 팔 수 있는 전체 객실 수 |
| 판매 수 | soldCount | 확정된 예약이 점유한 수 |
| 선점 수 | heldCount | Hold가 임시로 점유한 수 |
| 개설 | Open | 기간을 지정해 날짜별 재고를 한꺼번에 만드는 것 |
| 조정 | Adjust | 수량이나 금액을 고치는 것. 불변식 검사가 따른다 |
| 선점 | Hold | heldCount를 올리는 것 |
| 확정 | Commit | heldCount를 내리고 soldCount를 올리는 것 |
| 반환 | Release | heldCount 또는 soldCount를 내리는 것 |
| 반환 원천 | source | ReleaseInventory가 내릴 카운터를 지정하는 값. HELD(선점 수) 또는 SOLD(판매 수) (v9 추가, 06-2 5-3) |
| 요금 | Rate | 호스트가 등록한 날짜별 1박 단가. 0보다 크다 |

재고와 가용성을 구분하는 것이 이 컨텍스트의 핵심이다. 재고는 저장된 값이고 가용성은 매번 계산되는 값이다.

## 4. 프로모션 용어 (2026-09-04 v10: 판정 시점 확정, 단수 규칙 확정)

| 한국어 | 영문 | 정의 |
|---|---|---|
| 프로모션 | Promotion | 운영자가 만든 자동 적용 할인 정책 |
| 적용 조건 | Condition | 최소 숙박일, 지역, 기간 |
| 할인율 | discountRate | 정률 할인의 비율 |
| 캠페인 기간 | campaignPeriod | 프로모션이 적용되는 달력상 기간. 시작일과 종료일을 모두 포함한다(양끝 포함). 적용 여부는 예약 생성 시점이 이 기간 안인지로 판정한다 (v10: 확정. 스냅샷이 생성 시점에 동결되기 때문). 숙박 기간(StayPeriod, 반열림)과 포함 규칙이 다르다 |
| 할인 배분 | Allocation | 예약 전체에 계산된 할인 총액을 숙박 날짜별 단가에 비례해 나눠 금액 스냅샷에 날짜별로 기록하는 것. 배분액의 합은 할인 총액과 정확히 일치해야 한다. 나누어떨어지지 않는 단수는 날짜별 비례 내림 후 마지막 날짜 행에 가산한다 (v10: Step 7 확정) |
| 상태 | OPEN, CLOSED | 프로모션의 두 상태. CLOSED는 다시 열리지 않는다 (v9 추가, 06-2 I13) |
| 생성 | Create | 없던 프로모션을 새로 만드는 것 |
| 종료 | Close | 더 이상 적용되지 않게 닫는 것. 삭제가 아니다. 종료된 프로모션은 수정할 수 없다 (v10) |

캠페인 기간과 숙박 기간을 반드시 갈라 쓴다. 9월에 파는 12월 숙박 상품에 붙는 할인이라면 캠페인 기간은 9월이고 숙박 기간은 12월이다. 생성 후 캠페인이 끝나도 이미 만든 예약의 할인은 유지된다(R5).

## 5. 예약 용어 (2026-09-04 v9: 스냅샷 구성 명시, 날짜별 가격 행 추가)

| 한국어 | 영문 | 정의 |
|---|---|---|
| 예약 | Booking | 이용자가 특정 객실 타입을 특정 기간 묵겠다고 만든 계약. 생성 시점부터 재고를 붙잡는다 |
| 선점 중 | HELD | 생성됐고 결제가 끝나지 않은 상태. 재고를 임시로 붙잡고 있고 TTL이 돈다 (v5) |
| TTL | ttl | HELD가 유지되는 시간. 값은 설정 파라미터 (기본 10분 [가설], Step 9) |
| 확정 | CONFIRMED | 결제 승인으로 예약이 성립한 상태 |
| 취소 | CANCELED | 확정된 예약을 이용자가 무른 상태 |
| 만료 | EXPIRED | TTL 만료 또는 결제 실패 한도 도달로 HELD가 종료된 상태. 붙잡았던 재고는 반환된다 (v5: 정의 확장) |
| 만료시키기 | ExpireBooking(reason) | HELD 예약을 EXPIRED로 보내는 커맨드. reason은 TTL_EXPIRED 또는 PAYMENT_FAILED (v6). 이미 EXPIRED면 재호출 무해 (v10) |
| 체크인 | checkIn | 숙박이 시작되는 날. 이 날부터 재고를 점유한다 |
| 체크아웃 | checkOut | 숙박이 끝나는 날. 이 날은 재고를 점유하지 않는다 |
| 숙박 기간 | StayPeriod | 체크인부터 체크아웃까지. 박수는 두 날짜의 차이 |
| 연박 | Multi-night | 박수가 2 이상 |
| 인원 | userCount | 묵는 사람 수. 신청 시점의 maxOccupancy를 넘을 수 없다 (v8: guestCount에서 개명) |
| 이용자 식별자 | userId | 예약을 만든 이용자. v1에서 Booking이 가진 유일한 이용자 정보 (v8: guestId에서 개명) |
| 금액 스냅샷 | PriceSnapshot | 생성 시점의 날짜별 단가와 할인 배분액, 적용 프로모션 식별자와 이름(적용 없으면 null), 총액을 복사해 보관한 것. 결제 청구액의 근거이며 총액은 저장값이다 (v10: 총액 저장 확정) |
| 날짜별 가격 행 | DailyPrice | PriceSnapshot 안의 날짜 하나. 그날의 단가와 할인 배분액 (v9 추가, 06-2) |
| 멱등키 | idempotencyKey | 같은 요청이 반복돼도 예약이 하나만 생기게 하는 식별자. 같은 키의 재요청은 기존 예약을 반환한다 (v10: 응답 확정) |

상태 전이는 HELD → CONFIRMED, HELD → EXPIRED, CONFIRMED → CANCELED 셋뿐이다. CONFIRMED → EXPIRED는 없다.

## 6. 결제 용어 (2026-09-04 v10: REFUNDED 전이 명시)

| 한국어 | 영문 | 정의 |
|---|---|---|
| 승인 | Approved | PG가 결제를 성공 처리한 것 |
| 실패 | Failed | PG가 결제를 거절한 것 |
| 환불 | Refunded | 승인된 결제를 되돌린 것 |
| 콜백 | Callback | PG가 결과를 우리에게 통보하는 호출 |
| 청구액 | Amount | PG에 청구한 실제 금액. 예약이 실어 보낸 스냅샷 총액과 일치해야 한다 (v10) |
| 결제 시도 | PaymentAttempt | Payment 안의 하위 엔티티. 한 번의 PG 요청과 그 결과. FAILED 이후의 재시도는 상태 역행이 아니라 새 시도 생성이다 (v9 추가) |
| 결제 상태 | PaymentStatus | 시도의 상태다. REQUESTED에서 APPROVED 또는 FAILED로, APPROVED에서 REFUNDED로만 전이한다. Payment 자체는 저장 상태 없이 시도 목록에서 계산한다 (v10: 전이 명시) |
| 결제 시도 횟수 | attemptCount | 이 예약에 대한 결제 시도 누적 수. 3을 넘을 수 없다. 저장하지 않고 시도 목록에서 계산한다 (v9) |
| 거래 식별자 | pgTransactionId | PG가 발급한 거래 번호. 같은 번호의 콜백이 다시 오면 승인이든 실패든 무시한다 (v9: 실패까지 확장) |

## 7. v1 범위 밖 (2026-09-02 v8: 표기 갱신)

- 회원: 이용자는 userId로만 식별
- 쿠폰: 전체
- 호실 배정: 객실 타입까지만
- 알림, 정산, 리뷰
- 호스트나 운영자에 의한 예약 취소
- 프로모션 자동 종료

## 8. 서비스 이름 후보 (2026-09-04 v9 추가. Step 9에서 확정)

애그리거트가 아닌 조율자들의 이름 후보다. 도메인 용어는 아니지만 문서 간 교차 참조를 위해 여기 둔다.

| 이름 후보 | 성격 | 소속 | 책임 요약 |
|---|---|---|---|
| InventoryAllocationService | 도메인 서비스 | 재고와 요금 | 연박 N행에 hold, commit, release를 원자적으로 적용 (06-2) |
| InventoryApplicationService | 앱 서비스 | 재고와 요금 | 개설 N행 생성, 조정, roomTypeId 존재 확인 |
| BookingApplicationService | 앱 서비스 | 예약 | 트랜잭션 경계. 재고와 결제 호출, RequestPayment 중계 |
| PricingService | 도메인 서비스 | 예약 [가설] | 단가와 프로모션을 읽어 DailyPrice 행과 할인 배분 계산 |
