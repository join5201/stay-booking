## 0. 이 리포트의 전제 (반드시 읽을 것)

### 0-1. 실행 맥락과 해석

08-1(09-05)은 정책 축 블라인드 감사를 끝내고 7절에 해결안을 적은 뒤 8절 5항에 "사용자 판정이 문서에 나타나기 전까지 같은 검증을 반복하지 않는다"고 적었다. 09-06 현재 08-1 이후 프로젝트 문서 변경은 없다. 사용자 판정은 아직 없다.

예약 작업 프롬프트는 "직전의 답변이 있다면 그 답변을 해결하기 위한 방법을 제시하고 진행하라"다. 같은 문서를 같은 축으로 다시 감사하면 08-1과 같은 지적이 나올 뿐이므로, 이번 실행은 검증 대상을 옮겼다. 직전 답변의 해결안 자체를 후보안 스펙으로 만들어 공격시키고, 거기서 나온 구멍을 메운 해결안 v2와 수용 시 바로 반영 가능한 변경 목록을 만든다. 설계 문서를 바꾸는 것은 스킬 규칙(검증 결과를 근거로 사용자 확인 없이 설계 결정 바꾸기 금지)에 걸리므로 하지 않았다.

## 2. 에이전트 D 상세 (독립 재도출, 원문 그대로)

Thought: 네 결정의 공통 뿌리는 하나다. Outbox를 뺀 상태에서 "커밋 후 발행"은 전달 보장이 0인데, A4는 계약표에 정식 불변식(테스트 문장 있음)으로 올라 있다. 보장 없는 메커니즘 위에 보장을 선언한 것이라, 어느 후보를 고르든 A4를 지키려면 무언가를 더 두거나 A4를 강등해야 한다.
Observation: 06-2 §4는 "PaymentApproved 유실 시 수동 환불 대상은 학습 범위로 감수"라고 적고, 06-4 §1-1 A4는 "CONFIRMED로 끝나거나 EXPIRED + 환불로 끝난다"고 적는다. 두 문장은 같은 문서군 안에서 서로를 부정한다. 이 모순이 결정 1~4 전부의 판단 기준을 흔들기 때문에, 후보마다 "A4를 지키는가, A4를 강등하는가"를 명시했다.

### 결정 2. PaymentApproved 도착 시 가드 평가 시점

먼저 문제를 정확히 재현한다. 06-4 §2-2는 "가드가 상호 배타(HELD와 EXPIRED)라 둘 다 발동하는 일은 없다"고 결론짓지만, 상호 배타는 동시 발동을 막을 뿐 동시 침묵을 막지 않는다.

```
t0  콜백 트랜잭션 커밋 (Payment: REQUESTED → APPROVED)
t1  P2 리스너 먼저 실행 → Booking 읽음 → HELD → 가드 거짓 → 침묵, 종료

결과: 확정도 환불도 없음. 승인분 고아. A4 위반.
```

### 결정 3. PG 콜백과 PaymentAttempt를 잇는 식별자 규칙

현행 문서가 정한 매칭 규칙은 사실상 하나다: recordApproval의 선행조건 "REQUESTED 존재" + I9("REQUESTED는 동시에 하나") + U4(pgTransactionId 중복 무시). pgTransactionId는 중복 판정에만 쓰이고 어느 시도인지 고르는 데는 안 쓰인다. 그래서 다음이 뚫린다.

```
1차 시도 REQUESTED → (PG 응답 지연) → 어떤 경로로든 1차 종결 → 2차 시도 REQUESTED
→ 1차의 지연 승인 콜백 도착 (pgTransactionId는 신규 → U4 통과)
→ "REQUESTED 존재" 참 (2차가 REQUESTED) → 1차의 승인이 2차 시도에 기록됨
```
R6("예약당 승인된 결제 하나")은 I7이 지켜주지만, PG에는 승인이 둘 남고 우리 장부에는 하나만 남는 불일치가 생긴다. 금액이 같아도 거래번호가 어긋나 환불 시 엉뚱한 거래를 취소한다.

### 확인필요

1. 이벤트 발행 메커니즘의 구체. 06-4 §2-3의 "커밋 후 발행된 이벤트를 별도 트랜잭션에서 처리"가 @TransactionalEventListener(AFTER_COMMIT) 동기 실행인지 @Async 병용인지가 없다. 결정 1의 1-A와 1-B는 이 한 줄로 갈리고, 유실 창 크기와 예외 전파 여부가 정반대다.
2. Mock PG의 콜백 계약. 요청 시 우리 주문번호를 실을 수 있는지, 콜백이 그것을 되돌려주는지, pgTransactionId를 요청 시점에 받는지 콜백에서 처음 받는지. 결정 3의 3-A/3-B는 전부 이것에 달려 있다. "Mock"이라 우리가 정한다면 그 자체가 결정 사항이므로 요청자 판단이 필요하다.
3. PG의 재전송 정책. 5xx 응답 시 재전송하는지, 몇 회 어떤 간격인지. 1-A가 "PG 재전송을 재시도로 삼는다"를 성립시키려면 필요하고, 성립하지 않으면 1-A는 1-B와 유실 특성이 같아진다.
4. TTL 값, 콜백 타임아웃 값, 스케줄러 주기. 문서 어디에도 없다. 4-A의 성립 조건(타임아웃 < TTL)과 2-D의 창 크기(주기)가 여기서 결정된다.
5. 배포 인스턴스 수. "단일 Spring Boot 모듈"은 모듈 수이지 인스턴스 수가 아니다. 다중 인스턴스면 T1과 새 스케줄러들이 중복 실행되고, 06-4 §0의 "종착 재호출 무해"에만 의존해 정합성을 지켜야 한다. 비관적 락 범위(DB 행 락)로는 스케줄러 중복 자체는 못 막는다.
6. A4를 지킬 것인지 강등할 것인지. 이건 내가 도출할 수 없는 범위 결정이다. 06-2 §4는 감수한다고 하고 06-4 A4는 보장한다고 한다. 어느 쪽이 확정인지에 따라 1-D(스케줄러 +1, 정책 8→9)와 1-E(변화 0)가 갈린다.
7. "수동 개입"의 실행 주체와 창구. v1은 알림, 운영자 커맨드, 정산이 전부 범위 밖이다. 고아 승인과 REQUESTED 갇힘을 "수동"으로 처리한다면 그 수동이 무엇을 가리키는지(DB 직접 수정인지, 커맨드를 하나 추가하는지)가 필요하다.
8. 고아 승인이 I7의 "승인 유일" 셈에 들어가는지. 3-D를 채택할 경우 I7의 테스트 문장("승인 이력 시도는 하나를 넘지 않는다")이 고아를 포함하는지 배제하는지에 따라 R6 판정이 달라진다. 문서에 고아 개념 자체가 없어 유추할 근거가 없다.

#### 막혔다고 확인한 공격 (요약 목록)

- 중복 PaymentApproved가 CONFIRMED 예약을 환불: R-2의 CONFIRMED 무해 분기. base 03 §5-3이 우려한 오폭이 통합 핸들러에서도 유지됨.
- 잠금 순서 교착: 문서화된 모든 경로가 Booking → (재고 N행 오름차순 | Payment) 단일 방향이다. R-2, R-3, R-9 모두 Booking 선행이고, recordApproval/recordFailure는 Payment만 잠그며 Booking을 요구하지 않고, 취소 환불은 R-7로 커밋 후이므로 Booking 잠금을 들고 있지 않다. RequestBooking은 재고 행만 잠그고 기존 Booking 행을 기다리지 않는다. 순환 대기가 만들어지지 않는다. 다만 이 전역 순서를 명시한 곳은 R-2 한 줄뿐이고 base 06-4 §0에는 없으므로, §0의 락 항목으로 승격할 것을 권한다.
- T1 대 T2, 다중 인스턴스 동시 처리로 인한 재고 이중 연산 (I1, I1a): 후보 조회는 잠금 없이 해도 처리는 Booking 비관적 잠금 + 상태 재검사이고(R-5), §0의 종착 무해가 "무해로 답한 메서드는 전이 없음을 반환해 후속 재고 연산도 함께 생략"을 규정해 commit/release가 두 번 실행되지 않는다.
- BookingConfirmed / BookingExpired / BookingCanceled 이벤트 유실에 의한 재고 누수: 세 경로의 재고 연산이 전부 같은 트랜잭션 안(A2, A3, R-7)이라 이벤트 유실이 재고에 영향을 주지 않는다. R-1의 최대 1회 전달이 재고 불변식을 위협하는 지점은 없다.
- 동일 멱등키 동시 요청으로 인한 재고 이중 선점 (R3): U1 DB 유니크로 한쪽이 실패하고 그 트랜잭션의 선점이 함께 롤백된다(1-2 RequestBooking "실패 시 전체 롤백").
- 승인 후 재결제로 승인 2건 만들기 (I7): openAttempt Pre "승인 이력 없음(I7)"이 Payment 루트 잠금 아래서 검사된다.
- 만료 직전/직후 새 결제 시도 열기: R-9의 잔여 TTL 검사가 음수 잔여도 포함해 거부한다.
- 동시 RequestPayment 2건으로 REQUESTED 2개 만들기 (I9): R-9의 Booking 잠금 + openAttempt의 I9 검사로 직렬화.
- HELD 예약 취소로 CONFIRMED 전이표 우회 (I5): cancel Pre가 CONFIRMED만 받는다.
- PG가 콜백마다 다른 pgTransactionId를 보내 U4 무력화: R-4가 attemptId + 대상 시도 상태(REQUESTED) 검사를 추가해 U4에만 의존하지 않는다.
- AdjustInventory와 commit/release의 수량 경합 (I1): adjust Pre "바꾼 totalCount가 soldCount + heldCount 이상" + 잠금.

### D5. confirm()과 expire()의 반환 규약 (E 보통 2, 3, F 보통 6, 7)
