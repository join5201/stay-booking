## 1. 검증 ID 대조표

계약 9절이 지정한 계약 테스트 ID는 T03과 T04와 T05 전부, T06과 T07 부분이다. 근거는 10-6 기능별 API와 검증 연결 표의 재고와 요금 행이다.

### 1-1. T03

11 검증 기준의 문장은 이렇다. 재고 일괄 등록 중 이미 존재하는 날짜 포함. 기대는 전체 실패, 새 날짜도 등록되지 않음이다.

| 판정 항목 | 결과 | 무엇이 확인했나 |
|---|---|---|
| 겹치면 전체 실패 | 통과 | V5. 세 날짜 중 가운데가 있는 상태로 일괄 등록하면 409 RESOURCE_ALREADY_EXISTS |
| 새 날짜도 등록되지 않음 | 통과 | 같은 테스트. 겹치지 않은 첫 날짜와 마지막 날짜를 리포지토리로 다시 읽어 없음을 확인 |
| 원래 있던 행이 안 바뀜 | 통과 | 같은 테스트. 가운데 날짜의 totalCount가 5 그대로 |
| 겹치지 않으면 전부 등록 | 통과 | INV-02 정상 경로. 세 날짜 중 to를 뺀 두 행 |
| 실제 HTTP에서 같은 결과 | 통과 | step6/http-calls.txt의 V5 호출. 409 |

T03 판정: 통과.

원자성을 코드로 만들지 않은 것이 이 항목의 요점이다. 겹치는 날짜가 있으면 예외를 던지고 트랜잭션이 통째로 되돌아간다. 부분 저장을 지우는 코드를 쓰면 그 코드 자체가 검증 대상이 된다. 되돌리는 일을 DB가 하므로 검증할 코드가 없다.

### 1-2. T04

문장은 이렇다. totalCount를 heldCount + soldCount 아래로 수정. 기대는 409와 기존 수량 유지다.

| 판정 항목 | 결과 | 무엇이 확인했나 |
|---|---|---|
| soldCount 아래로 수정이 거절된다 | 통과 | V1. 5로 열고 판매 3을 놓은 뒤 2로 조정하면 InventoryBelowOccupiedException |
| 기존 수량 유지 | 통과 | 같은 테스트. 거절 뒤 다시 읽어 totalCount 5, version 0 |
| 상태 코드가 409이고 코드가 INVENTORY_BELOW_COMMITTED | 통과 | InventoryApiTest. 실제 포트로 PATCH를 쳐서 확인 |
| 경계가 허용된다 | 통과 | 판매 3인 날을 3으로 조정하면 200. I1은 이상이지 초과가 아니다 |
| heldCount 아래로 수정이 거절된다 | 미완 | heldCount를 0보다 크게 만드는 경로가 없다. 아래 참고 |

T04 판정: 부분 통과.

heldCount 몫을 미완으로 적는 이유. 검사식은 `totalCount < soldCount + heldCount` 하나이고 두 항이 같은 식에 있다. 그러나 heldCount가 0보다 큰 상태를 이번 묶음의 코드로 만들 수 없다. 그 값을 올리는 행동이 hold이고 계약 2-2절로 범위 밖이다. 검사식이 두 항을 더한다는 사실과 그것이 테스트로 확인됐다는 사실은 다르다. 뒤쪽을 통과로 적지 않는다.

이 미완은 V2와 같은 뿌리다. V2도 hold와 commit과 release가 있어야 확인되고 2026-09-09 사용자 승인으로 예약 묶음에 이월됐다. T04의 heldCount 몫도 같이 간다.

### 1-3. T05

문장은 이렇다. 버전이 지난 재고와 요금 수정. 기대는 VERSION_CONFLICT와 최근 변경 유지다.

| 판정 항목 | 결과 | 무엇이 확인했나 |
|---|---|---|
| 재고에서 지난 version이 409 | 통과 | V6. 0으로 한 번 성공시킨 뒤 다시 0으로 치면 409 VERSION_CONFLICT |
| 최근 변경 유지 | 통과 | 같은 테스트. 거절 뒤 읽으면 성공했던 8이 남아 있다 |
| 요금에서 지난 version이 409 | 통과 | V6의 요금 몫. RATE-02 같은 방식 |
| 맞는 version은 200이고 1로 오른다 | 통과 | INV-03과 RATE-02 정상 경로 |
| 단위 수준에서도 같은 판정 | 통과 | DailyInventoryTest와 DailyRateTest의 지난 버전 조정 거절 각 1건 |
| 실제 HTTP에서 같은 결과 | 통과 | step6/http-calls.txt의 V6 호출 |

T05 판정: 통과.

D-2가 정한 두 겹이 여기서 나뉜다. 잠금은 같은 순간의 두 요청을 줄 세우고 version 대조는 낡은 화면에서 온 요청을 거절한다. 위 표가 확인한 것은 뒤쪽이다. 앞쪽인 비관적 잠금은 동시 요청 테스트가 있어야 확인되고 그것은 T08의 일이라 예약 묶음이다. 코드에는 `findForUpdate`로 들어 있다.

### 1-4. T06

문장은 이렇다. 체크아웃 날짜에 재고와 요금이 없음. 기대는 그 날짜를 숙박 대상에서 제외하므로 예약 가능이다.

| 판정 항목 | 결과 | 무엇이 확인했나 |
|---|---|---|
| 없는 날짜 조회가 오류가 아니다 | 통과 | INV-04와 RATE-03이 없는 날짜를 400이나 404가 아니라 200과 missingDates로 답한다 |
| 끝 날짜가 기간에서 빠진다 | 통과 | INV-02와 INV-04가 to를 제외한다. 체크아웃 날짜가 곧 to다 |
| 예약이 가능하다 | 미완 | BOOK 계열이 범위 밖이다 |

T06 판정: 부분. 재고와 요금 쪽 준비는 끝났다. 체크아웃 날짜에 재고가 없어도 조회가 실패하지 않고, 기간 표현이 끝 날짜를 빼는 규칙으로 일관돼 있다. 예약 가능 판정 자체는 예약 묶음이 한다.

### 1-5. T07

문장은 이렇다. 숙박 날짜 중 한 날에 요금 또는 재고 없음. 기대는 오류 코드 구분과 Booking과 Hold 없음이다.

| 판정 항목 | 결과 | 무엇이 확인했나 |
|---|---|---|
| 없는 날짜를 골라낼 수 있다 | 통과 | V10. 있는 날짜는 items에, 없는 날짜는 missingDates에 들어간다 |
| 재고 없음과 요금 없음이 구분된다 | 통과 | 경로가 inventories와 rates로 갈라져 있고 각각 missingDates를 따로 낸다 |
| 재고 0과 재고 미등록이 구분된다 | 통과 | 없는 날짜를 0으로 채우지 않는다. V10이 items 수와 missingDates 수를 따로 센다 |
| 오류 코드 구분 | 미완 | 예약 요청의 오류 코드는 BOOK 계열이 정한다 |
| Booking과 Hold 없음 | 미완 | 범위 밖 |

T07 판정: 부분.

세 번째 행이 이 묶음이 T07에 실제로 기여한 것이다. 없는 날짜를 0으로 채워 내보냈다면 예약 쪽이 두 상태를 구분할 근거를 잃는다. 재고 0은 팔 방이 없는 날이고 재고 미등록은 판매 계획을 세우지 않은 날이다.

## 3. 회고 질문 넷

### 3-1. 한 바퀴에 실제로 몇 분이 들었나

개발 55분, 대기를 빼면 39분이다. 앞 묶음의 72분보다 짧다. API는 아홉으로 같고 난이도는 더 높았는데 시간이 줄었다.

줄어든 이유가 셋이다.

| 이유 | 크기 |
|---|---|
| 3단계를 통째로 건너뛰었다 | 앞 묶음에서 20분 |
| 계약 개정이 0회였다 | 앞 묶음은 3회 |
| 층 구조와 예외 핸들러 골격을 그대로 썼다 | 6-2단계가 6분에 끝난 것이 그 값이다 |

두 번째가 제일 크다. 앞 묶음의 회고가 느린 것은 개발이 아니라 결정과 계약 왕복이라고 적었고, 그래서 이번에는 결정 셋을 1단계에 모아 한 번에 받았다. 그 처방이 실제로 들었다.

### 3-2. 하네스 때문에 늘어난 시간이 얼마인가

| 늘린 것 | 값어치 |
|---|---|
| 계약 8-1절의 테스트 목록 | V12가 여기 없었으면 이벤트 발행을 또 빠뜨렸다. 구독자가 없어 다른 테스트로는 안 잡힌다 |
| 결과 파일 사본과 g1 | 미실행을 통과로 못 바꾼다. 앞 묶음에서 실물로 겪은 구멍이다 |
| progress.md와 troubleshooting.md | 이번에는 그때그때 적었다. 앞 묶음처럼 여덟 행을 소급 기입하는 일이 없었다 |
| 답변 게이트 | 매 턴 한 번 |

늘어난 시간보다 이번에 더 눈에 띈 것은 하네스가 못 잡은 것이다. ClockConfiguration의 package 선언 누락은 테스트 79건이 전부 초록인 채로 커밋에 남았다. 게이트가 보는 것은 작업 폴더의 실행 결과이고 커밋된 트리가 아니다.

| 잡은 주체 | 무엇 | 건수 |

| 나 | V2가 확인 불가라는 것, T04의 heldCount 구멍, V9의 조회 반쪽이 6-2단계라는 것 | 3 |
| 사용자 | 진행 내역 정리 요청이 커밋 누락을 드러냈다 | 1 |

앞 묶음은 사용자가 여섯을 잡았고 이번은 하나다. 줄어든 것이 좋은 신호로만 보이지는 않는다. 그 하나가 가장 무거웠기 때문이다. 커밋 누락은 초록 테스트를 통과 근거로 삼는 한 계속 안 보인다.

이 항목이 D-3의 값어치를 다시 말해 준다. 블라인드 평가는 실행 결과가 아니라 코드와 문서를 대조한다. package 선언과 파일 위치가 어긋난 것은 그 방식이면 읽히는 종류다.

### 3-4. 동결 중 관찰이 몇 건 쌓였고 그중 실제로 필요한 것은 몇 건인가

이번 바퀴에 troubleshooting.md에 더한 행은 셋이다.

| 무엇 | 고쳐야 하나 |
|---|---|
| 커밋에 편집분이 빠져도 테스트가 초록 | 그렇다. 게이트가 작업 폴더만 본다. 커밋된 트리를 대상으로 도는 검사가 필요하다 |
| Docker 기동 중과 막힘을 못 가름 | 아니다. 알아 둘 것이다 |
| progress 행의 시각을 먼저 쓰고 시계를 나중에 봄 | 아니다. 순서를 바꾸면 된다 |

첫째가 이번 바퀴가 하네스에 남기는 제안이다. 앞 묶음이 남긴 넷 중 둘은 그 사이에 PR로 처리됐다.
