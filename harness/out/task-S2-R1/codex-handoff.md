# task-S2 R1 Codex 평가 전달서

최초 작성: 2026-09-08
최종 갱신: 2026-09-08 (작성)
성격: 사람이 읽고 실행하는 절차서다. 평가 입력이 아니다. 평가자에게 이 파일을 넘기지 않는다.

## 0. 한눈에

Codex에서 새 작업 둘을 연다. 하나에 하나씩 준다.

| 작업 | 붙여넣을 것 | 리포트 저장 위치 |
|---|---|---|
| 새 작업 1 (A) | 아래 2절 블록 | C:/Dev/potenup/99_projects/o2o/harness/reviews/task-S2-R1-A.md |
| 새 작업 2 (B) | 아래 3절 블록 | C:/Dev/potenup/99_projects/o2o/harness/reviews/task-S2-R1-B.md |

둘을 같은 대화에서 돌리지 않는다. A의 판단이 B에 새면 축을 둘로 나눈 의미가 없어진다. 한 평가자가 다 보면 그 안에서 우선순위가 고정된다는 것이 분할의 이유다.

## 1. 시작 전 확인

세 명령을 돌려 전부 PASS가 나오는지 본다. 30초면 끝난다.

```
node harness/tools/check.mjs fill harness/tasks/task-S2.md
node harness/tools/check.mjs fill harness/out/task-S2-R1/evaluate-A.md
node harness/tools/check.mjs fill harness/out/task-S2-R1/evaluate-B.md
```

기대값은 각각 88건, 25건, 25건 통과다.

왜 먼저 보나. 이 명령은 요청서에 적힌 sha256과 실제 파일의 바이트를 대조한다. 하나라도 FAIL이면 대상이 바뀐 것이고, 그대로 평가에 넘기면 리포트가 다른 판을 가리키게 된다. 그 리포트는 결정표와 대조할 때 G2에서 막힌다.

FAIL이 나오면 평가를 시작하지 말고 Claude Code에 돌아와 출력 줄을 그대로 붙인다.

## 2. Codex 새 작업 1 (A)

새 작업을 열고 아래를 그대로 붙인다.

```
아래 절대경로의 평가 요청서를 열어 그 지시대로 평가한다.

C:/Dev/potenup/99_projects/o2o/harness/out/task-S2-R1/evaluate-A.md

요청서 1절의 허용 입력 표에 있는 여섯 파일만 읽는다. 그 표에 없는 파일은 열지 않는다.
요청서 3절이 지정한 축만 적용한다. 없는 축을 만들어 적용하지 않는다.
요청서 6절의 출력 스키마와 보조 표를 그대로 쓴다.
리포트는 C:/Dev/potenup/99_projects/o2o/harness/reviews/task-S2-R1-A.md에 저장한다.
대상 파일을 수정하지 않고 사용자 대신 완료를 승인하지 않는다.
```

A가 보는 것은 03 v12의 컨텍스트 맵 축 여섯이다. 06 범례 v7에는 적용할 Step 축이 평가 기준에 없어서 준비 미완료로 기록하게 된다. 지적 0건이 아니라 준비 미완료다. 그 둘이 다르다는 것이 요청서 3절에 적혀 있다.

## 3. Codex 새 작업 2 (B)

다른 새 작업을 열고 아래를 그대로 붙인다.

```
아래 절대경로의 평가 요청서를 열어 그 지시대로 평가한다.

C:/Dev/potenup/99_projects/o2o/harness/out/task-S2-R1/evaluate-B.md

요청서 1절의 허용 입력 표에 있는 여섯 파일만 읽는다. 그 표에 없는 파일은 열지 않는다.
요청서 3절의 공통 축 셋만 적용한다. Step 축은 적용하지 않는다.
```

경로 대신 파일을 첨부해야 하는 환경이면 아래를 올린다. 작업마다 일곱 개다.

## 5. 두 작업에 공통으로 지켜야 할 것

| 항목 | 내용 |
|---|---|
| 대화 분리 | A와 B를 같은 대화에서 돌리지 않는다 |
| 읽기 범위 | 허용 입력 표 여섯 개 밖은 열지 않는다. 대상 문서가 인용하는 02, 04, 04-5, 05-3, 06-2, 06-4, 08-1, 08-3, 11도 표에 없으므로 읽지 않는다 |
| 쓰기 금지 | 대상 파일을 고치지 않는다. 리포트 파일만 만든다 |
| 확인필요 유지 | 문서만으로 판단이 안 서면 확인필요로 남긴다. 문맥 부족에서 오는 오판을 치명으로 올리면 멀쩡한 결정을 뒤집게 된다 |
| 보조 표 필수 | 원본 번호, 지적 ID, 심각도, 위반 기준 네 열. 판정 요약의 등급별 수와 이 표의 등급별 수가 같아야 한다. 어긋나면 리포트가 잘린 것으로 처리된다 |
| 지적 ID | A는 S2-R1-A-01부터, B는 S2-R1-B-01부터 |
| 0건과 완료의 구분 | 지적이 없는 것과 검증을 마친 것은 다르다. 못 본 범위는 미확인으로 적는다 |

## 6. 힌트로 새면 안 되는 것

평가자에게 말하지 않는다. 블라인드가 깨진다.

| 항목 | 왜 |
|---|---|
| 어느 결정이 어떤 근거로 내려졌는지 | 결정표 decisions-09-1.md는 허용 입력이 아니다. 문서 안의 근거만으로 판정하는지가 B의 축이다 |
| 어디가 약한지, 어디를 봐 달라는지 | 스킬 원문이 명시적으로 금지한다 |
| 이 판이 잘 나왔다는 자평 | 같음 |
| 이 라운드의 미결 3건 | 판 번호 충돌, 표기 규칙 문서용 축 부재, project-sync 반출 절차. 셋 다 하네스 사정이지 문서의 결함이 아니다. 평가자가 알면 그쪽으로 지적이 쏠린다 |

## 7. 리포트를 받은 뒤

1. 두 리포트를 harness/reviews/task-S2-R1-A.md와 task-S2-R1-B.md에 넣는다. 파일명이 이 형태여야 G2가 파일명만으로 1차 대조를 한다.
2. Claude Code에 돌아와 리포트가 들어왔다고 알린다.
3. 그러면 결정표 harness/decisions/task-S2-R1.md를 만들고 g2 --mode pre를 돌리는 단계로 넘어간다.
4. 수용 여부는 사람이 정한다. 확인필요 항목에 한해 반박할 수 있고 치명과 보통은 반박하지 않는다.
5. 재평가는 최대 1회다.

리포트가 불완전하거나 보조 표의 수가 어긋나면 통과로 기록하지 않는다. 그 경우도 Claude Code에 그대로 알린다.

이 전달서는 사람이 실행하는 절차서다. 평가자에게 넘기지 않는다.
