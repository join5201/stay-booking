## 0. 현재 적용 범위 (2026-09-07 v20: 로컬 v9에서 이식)

서비스는 Next.js 프론트, Spring 기반 Java 백엔드, MySQL을 사용해 로컬에서 개발하고 검증한다. 배포와 운영 준비는 제외한다. 생성과 수정은 Claude Code, 평가는 Codex의 별도 작업에서 수행하고 사용자가 결과를 전달한다. 별도 LLM API를 호출하지 않는다.

[API 명세 v2](C:/Dev/potenup/99_projects/o2o/document/11-o2o-api-spec.md)는 요청과 응답, 상태 처리, 멱등 규칙과 검증 시나리오를 정의한 초안이다. P01~P11은 제안값이다. TTL 10분, 수수료 0, 할인 선택 방식과 단일 트랜잭션 후보를 이 문서의 확정 전제로 자동 편입하지 않는다.

API 명세 v2는 로컬 계열 위에 서 있어 이 문서가 채택한 프로젝트 계열의 확정 결정(비관적 락, 잠금 순서, 확정 우선, Payment 모델, userId)과 어긋나는 곳이 있다. v3 대조 전까지 11의 T18과 T19를 계약 테스트로 옮기지 않는다.

### Step 9. 구현 매핑과 검증 (2026-09-07 v20: 로컬 v9의 작업표 이식)

패키지 구조, Repository, Entity와 VO, ArchUnit, 계약표의 테스트 변환(06-4 1-1 문장이 테스트 이름). API 명세의 상태와 응답 모델이 JPA 모델의 구조를 그대로 결정하지는 않는다.

| 작업 | 산출물 | 완료 조건 |
|---|---|---|
| 입력 고정 | 사용할 설계 버전, API ID, 채택한 정책 목록 | 미결 정책과 확정 정책 구분 |
| 구현 매핑 | 패키지, 저장 모델, 호출과 트랜잭션 경계 | 설계 계약의 책임과 코드 위치 연결 |
| 테스트 변환 | 단위, MySQL 통합, API와 동시성 테스트 계획 | API 명세의 T01~T30 중 해당 항목 연결 |
| 기능별 구현 계획 | 백엔드, 프론트, 연결 테스트 순서 | 기능 하나마다 검증 가능한 작업 크기로 분할 |

이월: 예외 이름 확정, 비동기 이벤트 전달 메커니즘, 갭 락 테스트, 설정값(ttl, 개설 상한, 통화, 폴링 주기와 배치 크기, PG 호출 타임아웃), 대리키 매핑, source 위치, 서비스 배치(PricingService 소속).

실 PG 전환 시 되돌릴 것(08-3 수용 시): 취소 환불 비동기와 Outbox, 결제 시도 타임아웃 스케줄러, PG 요청 커밋 후 호출, 환불을 REFUND_PENDING 커밋과 T2 재시도로 잠금 밖으로, 고아 환불 재시도 상한과 운영 알림.

Step 9 이후 실제 작업은 초기 세팅, 백엔드와 테스트 코드, 프론트, 연결 테스트, 최종 검증을 기능 단위로 반복한다. 백엔드 전체를 끝낸 뒤 프론트 전체를 시작하지 않는다. API 명세 작성만으로 Step 5~8의 미결 설계나 Step 9 실행이 완료되지는 않는다.

### 쟁점 4. 검색은 도메인 모델을 쓰지 않는다
조회 전용 쿼리와 DTO. 애그리거트 없음. 갱신은 읽기 모델 프로젝션(06-4 2-3, 지연 허용). 가용성의 출처가 프로젝션인지 조회 시 계산인지는 미정.

### 쟁점 5. Payment의 식별 단위 (해소)
예약당 하나와 시도 목록 (06-2 7-5).

## 6. JPA 엔티티를 도메인 모델로 쓸 때의 규칙

- 애그리거트 경계를 넘는 연관관계에 @ManyToOne을 쓰지 않는다. ID 타입 VO로 참조한다
- public setter를 만들지 않는다
- VO는 @Embeddable과 protected 기본 생성자와 값 기반 equals, hashCode
- 애그리거트 내부 컬렉션만 cascade와 orphanRemoval
- 검증 책임을 레이어로 분리한다 (06-4 1-4 위치 표)
