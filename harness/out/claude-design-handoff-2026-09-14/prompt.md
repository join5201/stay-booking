# 클로드 디자인 프롬프트: O2O 숙박 예약 MVP 화면 설계

최초 작성: 2026-09-14
최종 갱신: 2026-09-14

사용 방법: 구분선 아래를 그대로 Claude Design의 첫 메시지로 붙인다. 같은 폴더의 context.md를 그 메시지에 파일로 첨부하거나, 첨부가 안 되면 바로 다음 메시지로 전문을 붙인다. 이 머리(사용 방법까지)는 붙이지 않는다.

---

O2O 숙박 예약 서비스의 MVP 프론트 화면을 설계해 달라. 백엔드는 이미 완성돼 있고 API 33개가 고정돼 있다. 첨부한 컨텍스트 문서가 사실의 전부다. 거기 없는 기능, 필드, 상태를 만들어 내지 말고, 정하지 못한 것은 질문 목록으로 남겨라. 구현은 Next.js로 할 것이라 결과는 그쪽에서 옮겨 적기 쉬운 형태여야 한다.

## 1. 무엇을 만드나

| 역할 | 화면 범위 |
|---|---|
| 게스트 | 검색, 숙소와 객실 상세, 가용성과 예상 금액, 예약 요청, Mock 결제, 예약 목록과 상세, 취소 |
| 호스트 | 내 숙소 목록, 숙소와 객실 타입 등록과 수정, 날짜별 재고 달력, 날짜별 요금 달력 |
| 운영자 | 프로모션 목록, 등록과 수정, 사용 여부 끄기 |
| 공통 | 개발용 행위자 전환 컨트롤, 오류 표시 |

로그인 화면은 없다. 회원 기능이 이번 범위 밖이라, 화면 위쪽의 행위자 전환 컨트롤(host_001, host_002, operator_001, guest_001, guest_002, 그리고 공개)이 그 자리를 대신하고 그 값이 X-Dev-Actor-Id 헤더로 나간다. 실제 인증처럼 보이게 꾸미지 마라. 개발용이라는 것이 화면에서 드러나야 한다.

## 2. 순서

| 순서 | 낼 것 | 그 다음 |
|---|---|---|
| 1 | 화면 목록과 역할별 흐름. 화면마다 부르는 API ID와 시점. 컨텍스트 4절의 후보를 고쳐 써도 된다 | 내가 확인한다. 확인 전에 화면을 그리지 마라 |
| 2 | 게스트 흐름 화면. 검색, 숙소 상세, 객실 상세(가용성과 예상 금액), 예약 요청, 결제, 예약 목록, 예약 상세 | 확인 |
| 3 | 호스트 화면. 숙소와 객실, 재고 달력, 요금 달력 | 확인 |
| 4 | 운영자 화면과 공통 요소 | 확인 |
| 5 | 컴포넌트 목록, 디자인 토큰, 화면과 API 대응표, 질문 목록 | 끝 |

## 3. 반드시 지킬 것

| 항목 | 규칙 |
|---|---|
| 상태 | 예약 상태는 HELD, CONFIRMED, EXPIRED, CANCELED 넷뿐이다. 예약을 보여 주는 화면마다 네 상태의 모습이 있어야 한다. 이동은 HELD에서 CONFIRMED, HELD에서 EXPIRED, CONFIRMED에서 CANCELED 셋뿐이다 |
| 시간 | 선점 남은 시간은 응답의 expiresAt과 serverNow 차이로 센다. 브라우저 시계로 세지 않는다. 0이 되면 화면이 알아서 만료로 바꾸지 않고 예약 상세를 다시 읽는다 |
| 돈 | KRW 정수. 소수점 없음. 천 단위 구분과 원. 예약 상세의 금액은 예약 안의 스냅샷이고 다시 계산하지 않는다 |
| 날짜 | YYYY-MM-DD, 서울 날짜. 체크아웃 날은 숙박에 들어가지 않는다. 검색과 예약은 최대 30박, 재고와 요금 달력은 최대 366일 |
| 인원 | 1~100이고 객실 최대 인원 이하 |
| 수정 폼 | 호스트와 운영자의 수정은 응답의 version을 들고 있다가 그대로 보낸다. 409 VERSION_CONFLICT면 다른 곳에서 바뀌었다고 알리고 새로 읽기 버튼을 준다 |
| 재시도 | 예약 요청, 결제 요청, 취소는 멱등키를 쓴다. 같은 동작의 재시도는 같은 키, 새 동작은 새 키다. 화면에서 다시 시도 버튼과 새로 만들기 버튼을 구분한다 |
| 오류 | 컨텍스트 8절의 오류 코드마다 화면 반응 후보가 있다. 그대로 따르거나, 바꾸면 이유를 적는다 |
| 결제 | Mock 결제다. 카드 입력이 없다. 시도는 최대 3번. 보류면 처리 중 상태를 보여 주고 예약 상세를 다시 읽는다. 프론트에 결제 확정, 환불, Mock 결과 전달 API는 없다 |
| 프로모션 | 게스트가 고르지 않는다. 서버가 하나를 골라 적용하고 화면은 결과만 보여 준다 |
| 범위 | 컨텍스트 11절의 항목은 그리지 않는다. 나중을 위한 빈 자리도 두지 않는다 |
| 폭 | 게스트 화면은 모바일 폭 기준으로 먼저 그리고 데스크톱은 그 확장으로. 호스트와 운영자 화면은 데스크톱 폭 기준 |

## 4. 결과물 형식

| 산출물 | 형태 |
|---|---|
| 화면 목록과 흐름 | 표. 화면 ID, 역할, 진입 경로, 부르는 API ID와 시점 |
| 화면 설계 | 화면마다 기본, 로딩, 빈 결과, 오류의 네 모습. 예약 화면은 상태 넷을 더한다 |
| 컴포넌트 목록 | 표. 이름, 쓰이는 화면, 입력, 상태. 날짜 범위 선택, 금액 표시, 상태 배지, 남은 시간, 페이지 이동, 달력 격자, 행위자 전환은 반드시 들어간다 |
| 화면과 API 대응표 | 표. 화면 ID 행마다 API ID, 호출 시점, 성공 시 화면 변화, 실패 코드별 반응 |
| 디자인 토큰 | 색, 글자, 간격, 상태 배지 색. 브랜드 가정 없이 중립으로 |
| 질문 목록 | 컨텍스트로 정하지 못한 것. 결제 시뮬레이션 모드(APPROVE, DECLINE, DEFER)를 게스트 화면에 둘지 개발용 패널에 둘지가 첫 항목이다 |

화면 ID와 API ID는 나중에 구현과 평가에서 추적하는 열쇠다. 표에서 빠뜨리지 마라.

## 5. 하지 말 것

- 컨텍스트에 없는 API, 필드, 상태, 정렬, 필터를 만들지 마라.
- 회원가입, 로그인, 결제수단 입력, 쿠폰, 리뷰, 알림, 지도, 사진 업로드, 호스트의 예약 관리 화면을 그리지 마라.
- 영어 UI 문구를 쓰지 마라. 화면 문구는 한국어다. 상태 값의 한국어 표시는 컨텍스트 13절을 따른다.
- 색과 글꼴에 브랜드 가정을 넣지 마라.
- 확인을 기다리라고 한 자리에서 다음 단계로 넘어가지 마라.
