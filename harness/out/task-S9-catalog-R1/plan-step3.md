## 1. 네트워크로 나가는 호출 넷

전부 승인 대상이다. 순서가 중요하다. 1을 먼저 하고 그 응답으로 2의 값을 정한다.

| 번호 | 호출 | 무엇을 받나 | 왜 |
|---|---|---|---|
| 1 | GET https://start.spring.io/metadata/client | 제공되는 Spring Boot 판 목록, 기본값, 의존성 ID 목록. JSON 읽기만 | 판 번호와 의존성 ID를 기억으로 적지 않기 위해서다. 이 응답이 2의 파라미터 원천이다 |
| 2 | GET https://start.spring.io/starter.zip?파라미터 | Gradle 뼈대 zip 하나 | gradle 명령이 로컬에 없어 wrapper를 직접 만들 수 없다 |
| 3 | docker pull mysql:태그 | MySQL 이미지 | mysql 클라이언트가 로컬에 없다. 컨테이너로 띄운다. 태그는 실행 직전에 고정해 이 문서에 적는다 |
| 4 | gradlew 첫 실행 | Gradle 배포판과 Spring 의존성 | 빌드를 한 번도 안 돌리면 결과 파일 경로를 확인할 수 없다. D-1 다의 확정이 그 확인에 달려 있다 |

받는 파일이 어디에 떨어지는지.

| 호출 | 착지 |
|---|---|
| 2 | 임시 폴더에 받아서 풀고, 내용을 확인한 뒤 backend/로 옮긴다. zip을 저장소 안에 두지 않는다 |
| 3 | Docker 로컬 이미지 저장소. 저장소 파일 아님 |
| 4 | backend/.gradle/과 사용자 홈의 Gradle 캐시. 앞의 것은 이미 .gitignore에 있다 |

## 2. 뼈대에 요청할 값

1번 응답을 보기 전에는 확정이 아니다. 근거가 있는 칸만 지금 채운다.

| 파라미터 | 값 | 근거 |
|---|---|---|
| type | Gradle 프로젝트 | CLAUDE.md 3절이 백엔드 빌드 루트를 build.gradle로 적는다. .gitignore에도 backend/build/와 backend/.gradle/이 이미 있다 |
| language | java | 01 14행 |
| javaVersion | 17 | 로컬 실측값 Temurin 17.0.18 |
| packaging | jar | 로컬 실행만 한다. 배포는 범위 밖 |
| bootVersion | 미정 | 1번 응답의 기본값을 쓰고 그 값을 이 문서와 계약 9절에 적는다 |
| groupId와 패키지 | 결정 D-4 | 아래 3절 |
| artifactId와 name | 미정 | D-4가 정해지면 따라온다 |

의존성은 넷만 넣는다. 근거 없는 의존성은 넣지 않는다.

| 의존성 | 근거 |
|---|---|
| 웹 (Spring MVC) | 11 API 명세가 HTTP와 JSON이다 |
| JPA | 입력 팩 1절. JPA 엔티티가 도메인 모델을 겸한다 |
| MySQL 드라이버 | 01 14행 |
| 검증 | 06-4 1-4 검증 책임 위치 표. 형식 검증은 컨트롤러가 한다 |

보안과 액추에이터와 마이그레이션 도구는 넣지 않는다. 이번 단계에 근거가 없다. 각 의존성의 실제 ID 문자열은 1번 응답에서 확인해 쓴다.

## 3. 패키지 구조

근거 셋이다. 입력 팩 1절의 단일 모듈과 컨텍스트별 패키지 분리, 05-2 1절의 컨텍스트 영문명, 06-1 4절의 공유 커널은 shared 패키지.

이번 단계에서 만드는 것은 catalog와 shared 둘뿐이다. 나머지 넷은 이 Task 범위 밖이라 빈 폴더도 만들지 않는다.

```
{base}
  catalog
    domain
    application
    api
    infrastructure
  shared
```

층 이름의 근거는 06-4 1-4 검증 책임 위치 표다. 형식 검증은 컨트롤러(api), 규칙 검증은 애그리거트와 VO(domain), 컨텍스트를 넘는 선행조건은 앱 서비스(application), 유일성과 무결성은 DB(infrastructure)다. eval-criteria-code.md의 레이어 역전 축이 domain이 infrastructure를 참조하는지를 보므로 두 층은 반드시 갈라야 한다.

### D-4. base 패키지명

| 안 | 값 | 대가 |
|---|---|---|
| 가 | com.o2o | 문서 파일명이 전부 o2o로 시작해 문서와 코드가 같은 이름을 쓴다. 짧다 |
| 나 | com.staybooking | 저장소 이름과 같다. 대신 설계 문서 어디에도 이 이름이 없다 |
| 다 | com.o2o.stay | 둘을 합친다. 한 단계 깊어진다 |

추천은 가다. 설계 문서가 정본이고 코드가 그것을 따른다는 원칙에서, 문서가 쓰는 이름을 코드가 쓰는 편이 일관된다. 저장소 이름은 문서에 근거가 없다.

## 4. MySQL 컨테이너

설정을 명령 한 줄이 아니라 파일로 둔다. 파일이면 다음 세션이 같은 값으로 다시 띄울 수 있고 F5의 머리 주석을 붙일 수 있다.

| 항목 | 값 |
|---|---|
| 파일 | backend/docker-compose.yml |
| 이미지 태그 | 실행 직전에 고정해 이 문서에 적는다. 기억으로 적지 않는다 |
| 호스트와 포트 | 127.0.0.1. 포트는 충돌 확인 뒤 고정 |
| DB명 | o2o_catalog_test |
| 계정 | 이름만 파일에 적고 비밀번호는 환경변수로 받는다. 값은 저장소에 넣지 않는다 |

DB를 하나만 둔다. 계약 9절의 데이터 초기화 허용 범위가 o2o_catalog_test 안의 테이블뿐이라 개발용 DB를 따로 만들면 그 범위 밖이 된다. 10-6 38행이 개발 환경과 테스트 환경 분리를 적지만 3단계에는 아직 분리할 데이터가 없다. 4단계에서 테이블이 생길 때 다시 본다.

스키마 이력 관리 도구도 이번 단계에 넣지 않는다. 10-6 41행이 요구하지만 지금은 테이블이 하나도 없어 이력을 남길 대상이 없다. JPA의 스키마 자동 생성으로 시작하고 4단계에서 판정한다. 설정 키 이름은 뼈대를 받은 뒤 그 프로젝트의 실제 설정 파일에서 확인해 쓴다.

## 5. 살아 있음을 어떻게 확인하나

계약 8절 3단계가 헬스 체크 하나라고 적었다. 그런데 11 API 명세에 헬스 체크 경로가 없다.

이대로 공개 경로를 하나 만들면 두 곳에 걸린다. T8은 설계 문서 근거 없는 코드를 금지하고, eval-criteria-code.md의 API 계약 준수 축은 명세에 없는 경로를 만들었는지를 직접 묻는다.

| 안 | 내용 | 대가 |
|---|---|---|
| 가 | GET /health 같은 경로를 만든다 | 11에 없는 경로가 생긴다. 평가 축에 바로 걸린다 |
| 나 | 통합 테스트 하나가 확인한다. 스프링 컨텍스트가 뜨고 MySQL 연결이 열리는지 | 새 경로가 안 생긴다. 브라우저로 눈으로 볼 수는 없다 |
| 다 | 액추에이터를 넣고 개발 프로파일에서만 연다 | 의존성이 하나 늘고 그 근거가 설계 문서에 없다 |

추천은 나다. 3단계의 목적은 뼈대가 서고 DB에 붙는다는 사실 확인이고, 그 확인에 공개 경로가 필요하지 않다. 게다가 D-1 다가 요구하는 기계 판독 결과 파일은 테스트를 돌려야 나온다. 나로 가면 확인과 결과 파일 생성이 한 번에 끝난다.

나는 계약 8절 3단계 문구를 다시 읽는 것이라 사용자 확인이 필요하다. 계약을 고치는 것이지 코드를 문서에 맞추는 것이 아니다.
