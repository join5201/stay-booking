11 검증 기준의 문장은 이렇다. 숙소부터 재고와 요금까지 등록 후 조회. 판정 항목은 요청과 응답 스키마, 소유자, version 일치 셋이다.

| 판정 항목 | 결과 | 무엇이 확인했나 |
|---|---|---|
| 요청과 응답 스키마 | 통과 | CatalogApiTest의 응답 아홉 필드 타입과 값, 시각 형식, 상한 다섯 |
| 소유자 | 통과 | C6 셋. 응답 hostId가 헤더 행위자, body의 hostId는 400, 남의 숙소는 404 |
| version 일치 | 통과 | CAT-02 맞는 버전 200과 version 1, C4 틀린 버전 409와 값 불변 |
| 등록 후 조회 (숙소와 객실) | 통과 | CAT-01과 CAT-03, CAT-06과 CAT-08의 한 줄기 |
| 등록 후 조회 (재고와 요금) | 미완 | INV와 RATE 계열이 이 Task 범위 밖이다. 계약 3절 |

T01 판정: 부분 통과. 판정 항목 셋은 전부 닫혔고, 문장의 재고와 요금 구간만 남는다. 그 구간은 다음 묶음의 Task에서 닫는다. 통과로 적지 않고 부분으로 적는 근거는 계약 9절의 필수 검증을 실행하지 못했을 때 항이다. 실행하지 않은 것을 통과로 바꾸지 않는다.

## 3. 회고 질문 넷

### 3-1. 한 바퀴에 실제로 몇 분이 들었나

측정된 코드 작업은 72분이다. 그런데 이 값은 실제 소요의 일부다. 계약을 세 번 개정하고 결정 여섯을 받는 데 쓴 턴이 측정 밖에 있다.

다음 바퀴의 크기를 정하는 데 쓸 값은 72분이 아니라 이것이다. 개발 자체는 빨랐고 느린 것은 결정과 계약 왕복이었다. 그래서 다음 바퀴는 API 개수를 줄일 것이 아니라 결정을 앞에 모아야 한다.

### 3-2. 하네스 때문에 늘어난 시간이 얼마인가

정확히 재지 못했다. 다만 성격은 갈린다.

| 늘린 것 | 값어치 |
|---|---|
| 판 번호와 설정 키를 실물에서 확인 | 세 번 구했다. 캐시의 다른 판, 메타데이터 id와 파라미터 불일치, Jackson 3 전환 |
| 계약 개정 세 번 | 두 번은 값어치가 있었고 한 번은 앞의 실수를 되돌린 것이다 |
| 답변 게이트 | 매 턴 한 번. 형식은 지켜졌지만 내용의 정확성은 못 잰다 |
| 진행 기록과 트러블슈팅 | 이번에 여덟 행을 소급 기입했다. 그때그때 적었으면 없었을 일이다 |

뺄 후보는 없다. 대신 순서를 바꿀 것이 있다. 결정을 단계마다 묻지 말고 착수 전에 모아 묻는다.

### 3-3. 빌드와 테스트가 잡은 결함과 사람이 잡은 결함의 비율

이 질문의 답이 이번 바퀴에서 가장 분명하다.

| 잡은 주체 | 무엇 | 건수 |
|---|---|---|
| 빌드와 테스트 | DB 연결 실패, 헤더 한글 거부, 컴파일 오류 | 3 |
| 검사기 | 03 문서 해시 stale, 계약 빈칸 | 2 |
| 사용자 | 이벤트 발행 누락, 테스트 품질 셋, 기록 파일 미사용, 프론트 순서, API 개수 오도, bootRun 실패 | 6 |

사람이 잡은 여섯이 더 무겁다. 특히 이벤트 발행 누락은 테스트가 55건이어도 안 잡혔다. 테스트가 없는 기능은 테스트가 못 잡는다.

이 비율이 D-3에 대한 답을 바꾼다. 이번에는 나로 정했지만, 사람이 잡은 여섯 중 넷은 설계 문서와 코드를 대조하면 나오는 것이었다. 그것이 블라인드 평가가 하는 일이다. 다음 묶음에서는 다로 가는 쪽을 권한다.

### 3-4. 동결 중 관찰이 몇 건 쌓였고 그중 실제로 필요한 것은 몇 건인가

이번 바퀴의 트러블슈팅 행은 15건이다. 그중 하네스를 실제로 고쳐야 하는 것은 넷이다.
