작성일: 2026-09-01
최종 갱신: 2026-09-02 v2 (v9 Hold 흡수 동기화, 상위 입력 경로 정정)
용도: DDD 산출물을 블라인드 서브에이전트에게 검증시킬 때 전달하는 유일한 배경 문서다.

## 0. 이 문서의 존재 이유

검증 에이전트에게 ddd-plan.md를 통째로 주면 안 된다. 그 문서 3장과 4장에는 쟁점에 대한 권고와 근거가 들어 있고, 그걸 읽은 에이전트는 권고를 정당화하는 방향으로만 판정한다. 관점 고정을 깨려고 에이전트를 분리했는데 입력으로 다시 고정시키는 셈이다.

그래서 판정에 필요한 전제와 요구사항만 여기에 발췌해 둔다. 검증 프롬프트는 이 문서와 상위 입력 문서만 참조한다.

넣지 않는 것: 쟁점별 후보안, 권고안과 그 근거, 어느 방향이 유력한지에 대한 서술, 대화 이력.

## 1. 확정 전제

| 항목 | 결정 |
|---|---|
| 도메인 모델과 JPA 엔티티 | 분리하지 않는다 (JPA @Entity가 도메인 모델을 겸한다) |
| 프로젝트 구조 | 단일 Spring Boot 모듈 + 컨텍스트별 패키지 분리 |
| 결제 | Mock. 단 TTL 설계는 실제 PG 지연을 전제로 한다 |
| 쿠폰 | v1 제외 |
| 프로모션 | 자동 적용형만, 수량 제한 없음. 예약 흐름에서 읽기만 발생 |
| 채널 | 단일 채널. 오버부킹 대응 없음 |

## 2. 시스템 보장 요구사항 (5개)

- R1. 연박 중 한 날짜라도 재고 부족 시 전체 선점 실패
- R2. 동시 요청에서도 초과 예약 0
- R3. 동일 요청 재시도 시 중복 Booking 방지
- R4. HELD 종료 시 재고 반환 보장 (TTL 만료와 결제 3회 실패 중 먼저 오는 조건)
- R5. 확정된 Booking의 결제 금액은 이후 요금/프로모션 변경에 영향받지 않음

## 3. 확정된 도메인 규칙

기능 목록 3절에서 확정된 것 중 판정 기준이 되는 것만 옮긴다. (2026-09-02 v2: Hold 흡수 v9 반영)

- HELD 종료 경로는 둘이다. TTL 만료, 결제 3회 실패. 먼저 오는 쪽이 발동하며 둘 다 BookingExpired 하나로 끝난다
- 결제 2회 실패까지는 HELD를 유지한다. 3회째에 만료시킨다
- attemptCount는 3을 넘을 수 없다
- CancelBooking은 확정된 예약에만 적용된다. HELD 상태에는 취소 커맨드가 없다
- HELD 상태의 이탈은 TTL이 처리한다. 별도 커맨드를 두지 않는다
- HELD 종료는 스케줄러 또는 결제 실패 정책이 실행한다. ExpireBooking(reason) → BookingExpired → ReleaseInventory ×N → InventoryReleased ×N. reason은 TTL_EXPIRED 또는 PAYMENT_FAILED (v9: ExpireHold, ReleaseHold, HoldExpired, HoldReleased는 Hold 흡수로 폐기)
- BookingStatus 전이는 HELD → CONFIRMED, HELD → EXPIRED, CONFIRMED → CANCELED 셋뿐이다. CONFIRMED → EXPIRED는 없다
- 금액 스냅샷은 총액만이 아니라 날짜별 단가, 날짜별 할인 배분액, 적용 프로모션 식별자와 이름까지 Booking에 복사한다. 시점은 예약 생성 시다 (v2: 시점 명시)
- 프로모션에 인스턴스가 없으므로 할인 적용 사실은 오직 이 스냅샷에만 남는다

## 5. 독자 프로필

주니어 백엔드 개발자. Java, Spring Boot, MySQL, Docker, AWS. 이 설계 문서만 보고 코드를 짤 사람이며, 문서가 만들어진 논의는 알지 못한다. 자립성 판정의 기준점은 이 독자다.

## 6. 갱신 규칙

기능 목록이나 요구사항이 바뀌면 이 문서도 같이 고친다. 이 문서가 낡으면 검증 결과가 통째로 무효가 된다. 쟁점에 대한 결론이 확정되어 더 이상 열린 선택지가 아니게 되면, 그때 3절로 옮긴다. 열려 있는 동안에는 절대 옮기지 않는다.
