## 1. 기능 목록 (2026-09-07)

### 판매 준비
- 숙소 등록, 수정, 조회
- 객실 타입 등록, 수정, 조회
- 날짜별 재고 개설, 조정, 조회와 기간 일괄 개설
- 날짜별 요금 등록, 조정, 조회

### 프로모션
- 프로모션 생성, 수정, 조회
- 적용 가능 프로모션 조회
- 프로모션 수동 종료. API 초안에서는 enabled를 false로 두는 수정으로 표현한다. 등록과 조회에는 자동 적용 가능한 후보의 계산이 포함된다.

### 검색
- 지역, 날짜, 인원 기반 숙소 검색
- 객실별 연박 가용성 조회
- 예상 숙박 금액 조회

### 예약
- 예약 요청 (멱등키)
- 연박 재고 원자적 선점
- Booking 생성과 금액 스냅샷 저장
- Mock 결제 (실패 시 재시도 허용)
- 예약 확정과 재고 확정
- 예약 목록과 상세 조회
- 예약 취소 (확정된 예약만, 게스트만)
- Mock 환불
- 예약 취소에 따른 재고 반환

### HELD 예약 관리
- TTL 만료된 HELD 예약을 스케줄러가 만료시키고 재고 반환
- 결제 3회 실패 시 HELD 예약 만료와 재고 반환
- 후속이 남은 결제를 순찰 정책이 찾아 마무리 (2026-09-08 v9 추가)

## 2. 시스템 보장 요구사항 (2026-09-08 v9: R4 문언 교체, R6 신설)

- R1. 연박 중 한 날짜라도 재고 부족 시 전체 선점 실패
- R2. 동시 요청에서도 초과 예약 0
- R3. 동일 요청 재시도 시 중복 Booking 방지
- R4. HELD 종료 시 재고 반환 보장. 종료 조건은 TTL 만료와 결제 3회 실패 중 먼저 커밋되는 것이다. 단 만료 커밋 전에 승인이 기록됐으면 확정이 우선한다. 리스너 유실 시에도 늦어도 순찰 주기 안에 종료된다
- R5. 예약당 승인된 결제는 하나. 중복 콜백이 환불이나 이중 확정을 만들지 않음
- R6. Booking 생성 시 저장한 날짜별 단가, 할인과 총액은 이후 요금과 프로모션 변경에 영향받지 않음
- R7. 승인된 결제는 확정으로 소비되거나 환불로 되돌려지고, 그 사실이 정산 표식으로 남는다 (2026-09-08 v9 추가)

번호는 이 문서 안의 순서다. 06-4 v5 3절의 R1부터 R6까지와 대응이 다르므로 교차 인용할 때는 문장으로 가리킨다.

각 요구사항의 책임 컨텍스트는 01 Step 7 표에 매핑했다.

## 3. 확정된 설계 결정

### 3-1. 프로모션을 판매 준비에서 분리 (2026-08-27)

판매 준비에 남은 넷은 공급자가 등록하고, 객실 타입과 날짜 축에 붙으며, 예약 요청 전에 확정되어 있어야 한다. 프로모션은 셋 다 해당하지 않는다.

### 3-2. 쿠폰은 v1 범위에서 제외 (2026-09-01, v4에서 성격 재분류)

이것은 학습 범위 결정이다.

연박 재고 선점은 이 프로젝트에서 가장 어려운 동시성 문제다. 쿠폰의 선착순 수량 제한은 행 하나에 대한 조건부 UPDATE라 이 문제의 축소판이다. 동시성 학습을 재고 한 곳에 집중시키기 위해 v1에서 뺐다.

도메인 근거를 하나 덧붙이면, 자동 적용형 할인은 실제 숙박 플랫폼에서도 대부분 수량 제한이 없다. 다만 이건 부차적 근거이고 주된 이유는 학습 범위다.

효과는 둘이다. 프로모션이 예약 흐름에서 상태를 바꾸지 않고, 예약 요청이 직접 건드리는 애그리거트가 Booking 하나로 줄어든다.

### 3-3. HELD 예약의 종료 조건은 둘이고 종착은 EXPIRED 하나다 (2026-09-08 v9: 경합 문장 교체, Step 8 종결)

| 조건 | 트리거 | 비고 |
|---|---|---|
| TTL 만료 | 스케줄러가 HELD 예약을 찾아 ExpireBooking | 게스트가 이탈한 경우 포함 |
| 결제 3회 실패 | 세 번째 PaymentFailed 정책이 ExpireBooking | 2회까지는 HELD 유지 |

결제가 한 번 실패했다고 즉시 재고를 푸는 것은 선점의 존재 이유와 어긋난다.

두 조건 모두 BookingStatus를 EXPIRED로 보낸다. 결제 실패 종착을 별도 상태로 가르지 않는 이유는 v1에서 후속 처리가 같기 때문이다. EXPIRED의 정의를 TTL 만료 또는 결제 실패 한도 도달로 HELD가 종료된 상태로 넓힌다.

이 결정으로 생기는 것.
- 결제 시도 횟수는 Payment가 센다. PaymentFailed 이벤트에 횟수를 실어 보낸다
- 결제 실패 정책에 가드가 붙는다. PaymentFailed를 받고 attemptCount가 3 이상이면 ExpireBooking이다
- 불변식이 하나 생긴다. attemptCount는 3을 넘을 수 없다
- 만료 커밋이 승인 기록 커밋보다 먼저면 TTL이 이긴다 (2026-09-08 v9: 먼저 오는 것에서 먼저 커밋되는 것으로 교체)

두 조건이 동시에 걸리는 경합이 있다. 3회째 결제 요청이 PG에 가 있는 동안 TTL이 만료되면 BookingExpired 이후 PaymentApproved가 도착한다.

경합의 처리는 확정 우선이다. TTL에 도달한 HELD를 처리할 때 미정산 승인 결제가 있으면 만료시키지 않고 확정한다. 이미 EXPIRED가 커밋된 뒤 도착한 승인은 환불로 처리한다. CONFIRMED와 CANCELED에 도착한 승인은 정산 표식만 찍는다. 침묵하지 않는 이유는 침묵하면 순찰 정책이 그 결제를 영원히 후보로 다시 집기 때문이다. 중복 승인은 결제 컨텍스트가 pgTransactionId로 걸러 이벤트 자체를 다시 내지 않는다. (2026-09-08 v9: 08-3 C-6과 결정 11-1)

이 절은 자료 03 기준으로 정책 조기 도입에 해당했다. Step 8에서 재판정했고 08-3 결정 11건으로 종결됐다.

### 3-4. HELD 상태의 이탈은 TTL이 처리한다 (2026-09-01)

게스트가 결제 페이지에서 뒤로 가거나 창을 닫는 경우 별도 커맨드를 두지 않는다. 따라서 CancelBooking은 확정된 예약에만 적용된다. TTL 값은 설정 파라미터이며 기본 10분이 [가설]이다.

### 3-5. Hold는 Booking에 흡수한다 (2026-09-01 v6: 결정)

재검증에서 BookingConfirmed 이후 Hold를 닫는 전이가 없어, TTL이 지나면 스케줄러가 확정 예약의 Hold까지 만료시키고 soldCount로 옮겨진 재고를 다시 반환하는 결함이 발견됐다.

Hold를 별도 애그리거트로 두고 닫는 전이를 추가하는 안(이벤트 25개)과 Booking에 흡수하는 안을 비교해 흡수를 택했다. Hold의 커맨드가 전부 Booking 상태에 종속돼 있었고, CONFIRMED에서 EXPIRED로 갈 수 없다는 상태 규칙 하나로 결함이 구조적으로 막힌다.

체인은 이렇게 줄었다. ExpireBooking(스케줄러 또는 결제 실패 정책, 선행조건은 상태가 HELD)에서 BookingExpired로, 그다음 ReleaseInventory N회와 InventoryReleased N회다.

StayHeld는 BookingCreated에 포함되고, HoldExpired와 HoldReleased는 BookingExpired로 합쳐졌다. 이벤트 24개에서 22개, 커맨드 23개에서 22개, 애그리거트 후보 8개에서 7개가 됐다.

커맨드는 2026-09-08 v9에서 SettlePayment가 추가되어 다시 23개가 됐다. 04 v10 1절에 있다.

### 3-6. 재고 점유는 커맨드로 요청한다 (2026-09-01 v4 추가)

예약이 재고 행을 직접 만지지 않는다. 재고 컨텍스트에 HoldInventory, CommitInventory, ReleaseInventory 커맨드를 보내고 재고가 자기 이벤트를 발행한다.

리뷰에서 지적된 가장 큰 구멍이었다. 이전 설계는 예약이 재고의 heldCount를 직접 올리는 구조라 재고 수량은 재고 컨텍스트만 바꾼다는 원칙을 위반했다.

### 3-7. 결제는 예약을 모른다 (2026-09-01 v7: 액터 정정)

결제가 청구액을 알기 위해 예약을 읽으면, 예약은 결제 이벤트를 구독하므로 둘이 서로 상류가 된다.

게스트가 RequestPayment를 보내면 예약 컨텍스트가 받아 PriceSnapshot 총액을 실어 결제 컨텍스트로 넘긴다. 결제는 예약을 읽지 않는다. RefundPayment와 SettlePayment는 예약 컨텍스트의 정책이 보낸다.

v6에서 RequestPayment를 BookingCreated 정책의 자동 발송으로 바꿨으나 재시도가 도메인 커맨드에서 사라지는 문제로 v7에서 게스트 커맨드로 되돌렸다. 순환을 끊는 것은 총액을 실어 보내는 쪽이지 누가 누르느냐가 아니었다.

2026-09-08 v9에서 예약이 결제에 조회 둘을 더 보낸다. 방향은 여전히 예약에서 결제 한 방향이라 순환이 생기지 않는다. 06-1 v2 R6에 있다.

### 3-8. 금액 스냅샷의 범위와 시점 (2026-08-27, v7에서 시점 명시)

총액만 저장하지 않고 날짜별 단가, 날짜별 할인 배분액, 적용 프로모션 식별자와 이름까지 Booking에 복사한다.

시점은 생성이다. 청구액이 스냅샷 총액이어야 하므로 결제 요청 전에 동결돼 있어야 한다. 확정 시점에 동결한다고 적혀 있던 곳들을 v7에서 생성 시점으로 통일했다.

## 6. API와 내부 처리의 연결 (2026-09-07)

| 기능 | API ID 또는 내부 처리 |
|---|---|
| 숙소와 본인 숙소 조회 | CAT-01부터 CAT-05 |
| 객실 타입 | CAT-06부터 CAT-09 |
| 날짜별 재고와 기간 일괄 등록 | INV-01부터 INV-05 |

| 검색, 가용성, 예상 금액 | SEARCH-01부터 SEARCH-03 |
| 예약 생성과 조회 | BOOK-01부터 BOOK-03 |
| 결제 요청과 시도 조회 | PAY-01, PAY-02 |
| 예약 취소 | BOOK-04 |
| 결제 결과 전달 | INTERNAL-01. 로컬 Mock 전용 |
| Hold, Confirm, TTL 만료와 재고 반환 | 예약 생성, 결제 결과와 시간 정책의 내부 처리 |
| Mock 환불과 정산 표식 | 취소, 만료 후 지연 승인, 순찰 정책의 내부 처리 |

서비스 API는 32개, 로컬 Mock API는 1개다. 프론트가 상태나 재고 수량을 직접 바꾸는 Confirm, Release, Refund, Settle API는 두지 않는다. API 명세의 JSON 예시와 계약 테스트는 서비스 계약 자료이며, 평가자의 모범 지적 예시와는 다르다.
